# Implementación del Módulo `specs`

## [1].motivacion

### ¿Por Qué Empezar por Specs?

El módulo `specs` es el **cimiento** del pipeline completo. Antes de escribir una sola línea de código en lexer, parser o renderer, necesitas definir:

- ¿Qué construcciones Markdown soportarás?
- ¿En qué orden se evalúan los patrones?
- ¿Qué información captura cada token?
- ¿Cómo se estructura cada nodo del AST?

Implementar specs primero te permite:

1. **Validar el diseño sin código complejo**: puedes revisar regex, orden y gramática sin lidiar con lógica de parsing.
2. **Evitar refactorizaciones masivas**: cambiar specs después de implementar lexer/parser es costoso.
3. **Documentar decisiones**: specs sirve como especificación viva del lenguaje.
4. **Facilitar testing**: puedes testear regex individuales antes de integrarlas.

### Problemas de NO Tener Fuente Única de Verdad

#### Antipatrón: Specs Duplicados

```python
# ❌ lexer.py
HEADING_REGEX = r"^#{1,6}\s+"

# ❌ parser.py
HEADING_LEVELS = {1, 2, 3, 4, 5, 6}

# ❌ validator.py
MAX_HEADING_LEVEL = 6
```

**Problema**: tres lugares definen "qué es un heading válido". Si cambias el límite a 4, debes recordar actualizar tres archivos.

#### Antipatrón: Orden Hardcoded

```python
# ❌ lexer.py
if line.startswith("#"):
    return tokenize_heading(line)
elif line.startswith("```"):
    return tokenize_fence(line)
elif line.strip() == "":
    return tokenize_blank(line)
else:
    return tokenize_text(line)
```

**Problema**: el orden está enterrado en cadenas de `if/elif`. Agregar un nuevo tipo requiere tocar lógica de control.

### Solución: Specs como Fuente Única

```python
# ✅ specs.py
BLOCK_ORDER = ["CODE_FENCE", "HEADING_ATX", "BLANK_LINE", "TEXT"]
TOKENS = {
    "HEADING_ATX": r"^(?P<level>#{1,6})\s+(?P<content>.+)$",
    "CODE_FENCE": r"^```(?P<lang>\w*)$",
    # ...
}

# ✅ lexer.py (solo consume specs)
for token_type in BLOCK_ORDER:
    pattern = TOKENS[token_type]
    if pattern.match(line):
        # ...
```

**Ventaja**: agregar/reordenar tokens solo toca `specs.py`. El lexer es genérico.

## [2].decisiones_arquitectonicas

### Decisión 1: ¿Dict vs Constantes para Tipos de Token?

#### Opción A: Diccionario Espejo (❌ No Recomendado)

```python
TOKENS = {
    "HEADING": "HEADING",
    "TEXT": "TEXT",
    # ...
}
```

**Problema**: redundancia sin valor. `TOKEN["HEADING"]` es idéntico a `"HEADING"`.

#### Opción B: Constantes Simples (✅ Recomendado para MVP)

```python
# No hace falta dict, usa strings directamente
TOKENS = ["HEADING", "TEXT", "BLANK_LINE"]
```

**Ventaja**: simple, directo, sin overhead.

#### Opción C: Enum Ligero (✅ Opcional para Proyectos Grandes)

```python
from enum import Enum

class TokenType(str, Enum):
    HEADING_ATX = "HEADING_ATX"
    TEXT = "TEXT"
    BLANK_LINE = "BLANK_LINE"

# Uso: TokenType.HEADING_ATX == "HEADING_ATX" → True
```

**Ventaja**: autocompletado en IDEs, validación en tiempo de escritura.  
**Desventaja**: más boilerplate para MVP pequeño.

**Decisión para este proyecto**: usar **strings directos** en MVP. Si crece, migrar a `Enum`.

### Decisión 2: ¿Lista vs Dict con Prioridades para BLOCK_ORDER?

#### Opción A: Dict con Prioridades Numéricas (❌ Redundante)

```python
PRIORITIES = {
    "CODE_FENCE": 1,
    "HEADING_ATX": 2,
    "TEXT": 99
}
# Luego ordenar: sorted(PRIORITIES, key=lambda k: PRIORITIES[k])
```

**Problema**: la prioridad es solo el **orden**. Una lista ya expresa orden.

#### Opción B: Lista Ordenada (✅ Recomendado)

```python
BLOCK_ORDER = [
    "CODE_FENCE",    # prioridad implícita: 0
    "HEADING_ATX",   # prioridad implícita: 1
    "TEXT"           # prioridad implícita: 2
]
```

**Ventaja**: el índice ES la prioridad. Reordenar es mover líneas.

**Decisión**: usar **lista ordenada**. Fuente única de verdad, sin duplicación.

### Decisión 3: ¿Regex Crudo vs Compilado?

#### Opción A: Regex Crudo en Cada Match (❌ Ineficiente)

```python
import re
for line in lines:
    if re.match(r"^#{1,6}\s+", line):  # compila cada vez
        # ...
```

**Problema**: regex se compila en cada iteración (O(n×m) donde m = líneas).

#### Opción B: Compilación Manual (⚠️ Verboso)

```python
HEADING_REGEX = re.compile(r"^#{1,6}\s+")
# ...
if HEADING_REGEX.match(line):
```

**Problema**: debes crear una variable por patrón.

#### Opción C: Regex Maestro Compilado (✅ Recomendado)

```python
# Unir todos los patrones en uno solo con grupos nombrados
MASTER = re.compile(
    r"(?P<HEADING>^#{1,6}\s+)|(?P<TEXT>^.+)",
    re.MULTILINE
)
```

**Ventaja**: una sola compilación, identificación automática por nombre de grupo.

**Decisión**: compilar **master regex** una vez al importar `specs.py`.

### Decisión 4: ¿Grupos Nombrados Obligatorios?

#### Opción A: Captura por Índice (❌ Frágil)

```python
match = re.match(r"^(#{1,6})\s+(.+)$", line)
level = len(match.group(1))  # grupo 1
content = match.group(2)     # grupo 2
```

**Problema**: si cambias el regex (agregar grupo), los índices se rompen.

#### Opción B: Grupos Nombrados (✅ Robusto)

```python
match = re.match(r"^(?P<level>#{1,6})\s+(?P<content>.+)$", line)
level = len(match.group("level"))
content = match.group("content")
```

**Ventaja**: semántica explícita, resistente a cambios de estructura.

**Decisión**: **grupos nombrados obligatorios** en todos los patrones.

## [3].block_order_detallado

### Estrategia: Específico → Genérico

El orden en `BLOCK_ORDER` determina qué patrón se prueba primero. **Regla de oro**: patrones específicos antes que genéricos.

#### Ejemplo de Orden Correcto

```python
BLOCK_ORDER = [
    "CODE_FENCE_START",   # muy específico: ^```
    "CODE_FENCE_END",     # muy específico: ^```$
    "HEADING_ATX",        # específico: ^#{1,6}\s+
    "HR",                 # específico: ^(---|\*\*\*)$
    "LIST_ITEM",          # específico: ^[-*+]\s+
    "BLANK_LINE",         # específico: ^\s*$
    "TEXT",               # genérico: ^.+ (catch-all)
]
```

### Casos Problemáticos

#### Problema 1: TEXT Antes de HEADING

```python
# ❌ Orden incorrecto
BLOCK_ORDER = ["TEXT", "HEADING_ATX"]
```

**Consecuencia**: la línea `# Hola` matchea `TEXT` (porque `^.+` captura todo) y nunca llega a `HEADING_ATX`.

**Solución**: `TEXT` siempre al **final**.

#### Problema 2: Setext Heading vs HR

Markdown tiene dos estilos de heading:

```markdown
ATX:
# Heading 1

Setext:
Heading 1
=========
```

El problema: la línea `===` también puede ser HR (regla horizontal).

```python
# ⚠️ Orden crítico
BLOCK_ORDER = [
    "SETEXT_UNDERLINE",  # debe ir ANTES de HR
    "HR",                # ---  puede confundirse con setext h2
]

TOKENS = {
    "SETEXT_UNDERLINE": r"^(?P<char>=+|-+)$",  # requiere contexto previo
    "HR": r"^(?:---|___|\*\*\*)$"              # standalone
}
```

**Solución avanzada**: Setext requiere "mirar atrás" (línea previa debe ser TEXT). Esto complica el lexer línea-por-línea. **Decisión MVP**: solo ATX headings inicialmente.

#### Problema 3: Code Fence Start vs End

```python
TOKENS = {
    "CODE_FENCE_START": r"^```(?P<lang>\w*)$",
    "CODE_FENCE_END": r"^```$"
}
```

Ambos matchean ` ``` ` (sin lenguaje). **Solución**:

- `CODE_FENCE_END` debe estar **antes** si el parser mantiene estado (`dentro_fence`).
- O hacer el regex más específico:
  ```python
  "CODE_FENCE_START": r"^```(?P<lang>\w+)$",  # requiere lenguaje
  "CODE_FENCE_END": r"^```$"                   # solo backticks
  ```

**Decisión**: en MVP, aceptar ambos casos (start puede no tener lang) y usar **estado en parser** para diferenciar.

### Tabla de Orden Típico

| Posición | Token | Justificación |
|----------|-------|---------------|
| 1 | `CODE_FENCE_*` | Muy específico, tiene precedencia sobre casi todo |
| 2 | `HEADING_ATX` | `#` al inicio es inequívoco |
| 3 | `HR` | `---`/`***` completo en línea |
| 4 | `LIST_ITEM` | `-`/`*`/`+` con espacio |
| 5 | `BLANK_LINE` | Línea vacía o solo espacios |
| 6 | `TEXT` | Catch-all, captura lo que no matcheó antes |

## [4].tokens_y_regex

### Estructura de Cada Entrada

Cada token debe tener:

1. **Nombre único** (clave del dict `TOKENS`)
2. **Regex con anchors** (`^` para inicio, `$` para fin si aplica)
3. **Grupos nombrados** para capturar datos relevantes

```python
TOKENS = {
    "NOMBRE_TOKEN": r"^(?P<grupo1>patrón)(?P<grupo2>patrón)$"
}
```

### Patrones Comunes para Markdown

#### Headings ATX

```python
"HEADING_ATX": r"^(?P<level>#{1,6})\s+(?P<content>.+)$"
```

**Explicación**:
- `^`: inicio de línea
- `(?P<level>#{1,6})`: captura 1-6 símbolos `#`
- `\s+`: uno o más espacios (obligatorio en ATX)
- `(?P<content>.+)`: contenido del heading (resto de línea)
- `$`: fin de línea

**Testeo**:
```python
import re
regex = re.compile(r"^(?P<level>#{1,6})\s+(?P<content>.+)$")
match = regex.match("## Introducción")
assert match.group("level") == "##"
assert match.group("content") == "Introducción"
```

#### Listas

```python
"LIST_ITEM": r"^(?P<indent>\s*)(?P<marker>[-*+])\s+(?P<content>.+)$"
```

**Explicación**:
- `(?P<indent>\s*)`: captura espacios de indentación (para listas anidadas)
- `(?P<marker>[-*+])`: marcador de lista (uno de los tres)
- `\s+`: espacio obligatorio después del marcador
- `(?P<content>.+)`: contenido del item

#### Code Fence

```python
"CODE_FENCE_START": r"^```(?P<lang>\w*)$"
"CODE_FENCE_END": r"^```$"
```

**Detalle**: `\w*` permite lenguaje opcional (` ```python ` o solo ` ``` `).

#### HR (Regla Horizontal)

```python
"HR": r"^(?:---|___|\*\*\*)(?:\s*)$"
```

**Explicación**:
- `(?:...)`: grupo no-captura (solo alternativas)
- Tres variantes: `---`, `___`, `***`
- `(?:\s*)$`: permite espacios al final (opcional)

#### Blank Line

```python
"BLANK_LINE": r"^\s*$"
```

**Explicación**: línea vacía o solo espacios/tabs.

#### TEXT (Catch-all)

```python
"TEXT": r"^(?P<content>.+)$"
```

**Explicación**: captura cualquier línea con al menos un carácter. Debe ser **último** en `BLOCK_ORDER`.

### Pitfalls Comunes

#### Greedy vs Non-Greedy

```python
# ❌ Greedy (captura demasiado)
r"^(?P<content>.+)$"  # .+ captura hasta el final

# ✅ Non-greedy (si necesitas delimitador)
r"^(?P<content>.+?)(?P<rest>...)$"
```

Para línea completa, greedy está bien. Para parsing interno (inline), usa `+?`.

#### Multiline Flags

```python
# ❌ Sin MULTILINE
re.match(r"^#", "line1\n# line2")  # no matchea line2

# ✅ Con MULTILINE (si procesas texto completo)
re.compile(r"^#", re.MULTILINE)

# ✅ En lexer línea-por-línea, no hace falta
for line in text.split("\n"):
    re.match(r"^#", line)  # ^ es inicio de string, no necesita flag
```

**Decisión**: en lexer línea-por-línea, **no usar `re.MULTILINE`** (procesas líneas individuales).

#### Escape de Caracteres Especiales

```python
# ❌ Sin escape
r"^***$"  # * es cuantificador, no literal

# ✅ Escape correcto
r"^\*\*\*$"
```

**Regla**: escapa `.*+?[]{}()\|^$` cuando los quieras literales.

### Testing de Regex Individuales

```python
def test_heading_regex():
    pattern = re.compile(r"^(?P<level>#{1,6})\s+(?P<content>.+)$")
    
    # Casos válidos
    assert pattern.match("# H1")
    assert pattern.match("###### H6")
    
    # Casos inválidos
    assert not pattern.match("####### H7")  # más de 6
    assert not pattern.match("#NoSpace")   # sin espacio
    assert not pattern.match(" # Indented") # con indent
```

**Estrategia**: testear cada regex en aislamiento antes de integrar en `BLOCK_ORDER`.

## [5].grammar_y_nodes

### Diferencia entre TOKENS y NODES

| Concepto | Nivel | Propósito |
|----------|-------|-----------|
| **TOKEN** | Lexer | Representa una **línea cruda** identificada |
| **NODE** | AST | Representa una **construcción semántica** |

**Ejemplo**:
- Token `HEADING_ATX` → Nodo `heading`
- Tres tokens `TEXT` consecutivos → Un nodo `paragraph`

### Definición de NODES

Lista de tipos canónicos de nodos AST:

```python
NODES = [
    "document",      # raíz del árbol
    "heading",       # h1-h6
    "paragraph",     # bloque de texto
    "list",          # ul/ol
    "list_item",     # li
    "code_block",    # pre>code
    "hr",            # hr
    "text",          # nodo hoja (contenido)
]
```

**Criterio**: un tipo de nodo por construcción HTML principal.

### GRAMMAR: Estructura de Cada Nodo

`GRAMMAR` define qué hijos puede tener cada nodo y qué metadatos requiere.

```python
GRAMMAR = {
    "document": {
        "children": ["heading", "paragraph", "list", "code_block", "hr"],
        "meta": []
    },
    "heading": {
        "children": ["text"],
        "meta": ["level"]  # 1-6
    },
    "paragraph": {
        "children": ["text"],
        "meta": []
    },
    "list": {
        "children": ["list_item"],
        "meta": ["ordered"]  # bool: True=ol, False=ul
    },
    "list_item": {
        "children": ["text"],  # MVP: sin nesting
        "meta": []
    },
    "code_block": {
        "children": [],  # sin hijos (contenido en meta)
        "meta": ["lang", "content"]
    },
    "hr": {
        "children": [],
        "meta": []
    },
    "text": {
        "children": [],  # nodo hoja
        "meta": ["value"]  # string de contenido
    }
}
```

### Uso de GRAMMAR en Validator

```python
def validate_node(node, grammar):
    node_type = node["type"]
    spec = grammar[node_type]
    
    # Verificar que hijos sean permitidos
    for child in node.get("children", []):
        if child["type"] not in spec["children"]:
            return error(f"{child['type']} no permitido en {node_type}")
    
    # Verificar que meta tenga claves requeridas
    for key in spec["meta"]:
        if key not in node:
            return error(f"{node_type} requiere meta '{key}'")
    
    return ok()
```

### Extensibilidad: Agregar Nuevos Nodos

**Escenario**: quieres agregar tablas.

1. Definir tokens en `TOKENS`:
   ```python
   "TABLE_ROW": r"^\|(?P<cells>.+)\|$"
   ```

2. Agregar a `BLOCK_ORDER` (antes de `TEXT`):
   ```python
   BLOCK_ORDER = [..., "TABLE_ROW", "TEXT"]
   ```

3. Definir nodos en `NODES`:
   ```python
   NODES.extend(["table", "table_row", "table_cell"])
   ```

4. Actualizar `GRAMMAR`:
   ```python
   GRAMMAR["document"]["children"].append("table")
   GRAMMAR["table"] = {
       "children": ["table_row"],
       "meta": ["alignment"]  # ["left", "center", "right"]
   }
   GRAMMAR["table_row"] = {
       "children": ["table_cell"],
       "meta": []
   }
   GRAMMAR["table_cell"] = {
       "children": ["text"],
       "meta": []
   }
   ```

**Ventaja**: el resto del sistema (lexer, validator) se adapta automáticamente porque consultan `specs`.

## [6].politicas_configurables

### ¿Qué Debe Ser Configurable?

| Configurable ✅ | Hardcoded ✅ | Justificación |
|----------------|--------------|---------------|
| `LIST_INDENT` (espacios) | Regex de sintaxis base | Varía por estilo (2 vs 4 espacios) |
| `MAX_HEADING_LEVEL` | Tipos de nodos (`document`, `heading`) | Puede ser 4 en docs técnicos |
| `ALLOW_HTML` | Escape de HTML en renderer | Seguridad configurable |
| `CODE_FENCE_CHAR` | Orden en `BLOCK_ORDER` | Algunos usan `~~~` en vez de ` ``` ` |

### Ejemplo de Políticas

```python
# Políticas globales (cargadas al inicio)
POLICIES = {
    "LIST_INDENT": 2,
    "MAX_HEADING_LEVEL": 6,
    "ALLOW_HTML": False,
    "CODE_FENCE_CHARS": ["```", "~~~"],
    "HR_CHARS": ["---", "***", "___"],
}
```

**Uso en regex**:
```python
def build_hr_regex(policies):
    chars = "|".join(re.escape(c) for c in policies["HR_CHARS"])
    return rf"^(?:{chars})(?:\s*)$"

TOKENS["HR"] = build_hr_regex(POLICIES)
```

### Estrategia de Carga

#### Opción A: Globals (✅ Simple para MVP)

```python
# specs.py
LIST_INDENT = 2

# parser.py
from specs import LIST_INDENT
if indent_count % LIST_INDENT == 0:
    # ...
```

#### Opción B: Contexto Explícito (✅ Mejor para Testing)

```python
# specs.py
def create_context(policies=None):
    return {
        "LIST_INDENT": policies.get("LIST_INDENT", 2) if policies else 2,
        # ...
    }

# parser.py
def parse(tokens, context):
    indent = context["LIST_INDENT"]
    # ...
```

**Ventaja**: puedes testear con configuraciones distintas sin tocar globals.

### Perfiles

Perfiles pre-configurados para distintos sabores de Markdown:

```python
PROFILES = {
    "strict": {
        "MAX_HEADING_LEVEL": 6,
        "ALLOW_HTML": False,
        "SETEXT_HEADINGS": False
    },
    "gfm": {  # GitHub Flavored Markdown
        "MAX_HEADING_LEVEL": 6,
        "TABLES": True,
        "TASK_LISTS": True,
        "STRIKETHROUGH": True
    },
    "custom": {
        # usuario puede sobreescribir
    }
}

def load_profile(name):
    global POLICIES
    POLICIES.update(PROFILES[name])
```

**Uso**:
```python
import specs
specs.load_profile("gfm")
# Ahora TOKENS incluye patrones de tablas
```

## [7].compilacion_master_regex

### Algoritmo de Unión de Patrones

El objetivo es crear **un solo regex** que combine todos los patrones, identificando cuál matcheó por el nombre del grupo.

```text
función compile_master_regex(BLOCK_ORDER, TOKENS):
    patrones ← []
    
    para cada tipo en BLOCK_ORDER:
        regex ← TOKENS[tipo]
        # Envolver en grupo nombrado externo
        patrón_envuelto ← f"(?P<{tipo}>{regex})"
        patrones.append(patrón_envuelto)
    
    # Unir con | (alternancia)
    regex_combinado ← "|".join(patrones)
    
    retornar re.compile(regex_combinado)
```

### Ejemplo Concreto

```python
BLOCK_ORDER = ["HEADING_ATX", "BLANK_LINE", "TEXT"]
TOKENS = {
    "HEADING_ATX": r"^#{1,6}\s+.+$",
    "BLANK_LINE": r"^\s*$",
    "TEXT": r"^.+$"
}

# Resultado:
MASTER_REGEX = re.compile(
    r"(?P<HEADING_ATX>^#{1,6}\s+.+$)|"
    r"(?P<BLANK_LINE>^\s*$)|"
    r"(?P<TEXT>^.+$)"
)
```

**Uso en lexer**:
```python
match = MASTER_REGEX.match(line)
if match:
    token_type = match.lastgroup  # nombre del grupo que matcheó
    token_data = match.groupdict()
```

### Performance: Compilar una Vez

```python
# ✅ Compilar al importar módulo
import re
MASTER_REGEX = compile_master_regex(BLOCK_ORDER, TOKENS)

# ✅ En lexer, solo usar
def tokenize(text):
    for line in text.split("\n"):
        match = MASTER_REGEX.match(line)  # no recompila
```

**Ventaja**: compilación regex es costosa (O(m) donde m = complejidad del patrón). Hacerlo una vez amortiza el costo.

### Debugging: Inspeccionar Qué Patrón Matcheó

```python
match = MASTER_REGEX.match("# Hola")
print(f"Matcheó: {match.lastgroup}")  # "HEADING_ATX"
print(f"Grupos: {match.groupdict()}")
# {'HEADING_ATX': '# Hola', 'BLANK_LINE': None, 'TEXT': None}
```

**Truco para debugging**:
```python
def debug_match(line):
    for token_type in BLOCK_ORDER:
        pattern = re.compile(TOKENS[token_type])
        if pattern.match(line):
            print(f"✓ {token_type}: {line[:30]}")
            return
    print(f"✗ No match: {line[:30]}")
```

## [8].evolucion_y_mantenimiento

### Cómo Agregar un Nuevo Tipo de Token

**Checklist interno** (no incluir en doc final, solo para ti):

1. Agregar regex a `TOKENS`
2. Insertar en posición correcta en `BLOCK_ORDER`
3. Agregar tipo de nodo correspondiente a `NODES` (si aplica)
4. Actualizar `GRAMMAR` con estructura del nodo
5. Testear regex en aislamiento
6. Testear integración en lexer
7. Actualizar parser para manejar nuevo token
8. Actualizar renderer para nuevo nodo

**Ejemplo**: agregar blockquotes (`> texto`).

```python
# 1. Regex
TOKENS["BLOCKQUOTE"] = r"^>\s+(?P<content>.+)$"

# 2. Orden (después de headings, antes de text)
BLOCK_ORDER = [
    "HEADING_ATX",
    "BLOCKQUOTE",  # ← nuevo
    "TEXT"
]

# 3. Nodo
NODES.append("blockquote")

# 4. Gramática
GRAMMAR["document"]["children"].append("blockquote")
GRAMMAR["blockquote"] = {
    "children": ["paragraph", "heading"],  # puede contener bloques
    "meta": []
}
```

### Migraciones cuando Cambia la Estructura

**Escenario**: cambias `meta` de `heading` de `level` (int) a `level_name` (string: "h1", "h2").

**Estrategia**:

1. **Versionado**:
   ```python
   SPEC_VERSION = "2.0.0"
   ```

2. **Migrador**:
   ```python
   def migrate_ast_v1_to_v2(ast):
       # Recorrer recursivamente
       if ast["type"] == "heading":
           level = ast.pop("level")  # remover viejo
           ast["level_name"] = f"h{level}"  # agregar nuevo
       for child in ast.get("children", []):
           migrate_ast_v1_to_v2(child)
   ```

3. **Detección de versión** (opcional):
   ```python
   ast = {
       "version": "1.0.0",
       "type": "document",
       "children": [...]
   }
   ```

### Testing de Compatibilidad hacia Atrás

## [9].antipatrones_comunes

### Antipatrón 1: Diccionarios Espejo

```python
# ❌ No hacer esto
TOKEN_NAMES = {
    "HEADING": "HEADING",
    "TEXT": "TEXT"
}
```

**Problema**: clave y valor son idénticos. No aporta nada.

**Alternativa**: usar strings directos o `Enum` si necesitas validación.

### Antipatrón 2: Prioridades Duplicadas

```python
# ❌ Dos fuentes de verdad
BLOCK_ORDER = ["HEADING", "TEXT"]
PRIORITIES = {"HEADING": 1, "TEXT": 2}
```

**Problema**: si cambias una lista, debes cambiar la otra.

**Solución**: `BLOCK_ORDER` es la única fuente. El índice es la prioridad.

### Antipatrón 3: Regex sin Escape

```python
# ❌ * es cuantificador, no literal
TOKENS["HR"] = r"^***$"
```

**Error resultante**: `sre_constants.error: multiple repeat`

**Solución**: escapar caracteres especiales.
```python
TOKENS["HR"] = r"^\*\*\*$"
```

### Antipatrón 4: Validación en Specs

```python
# ❌ No hacer esto
TOKENS = {
    "HEADING_ATX": (r"^#{1,6}\s+.+$", validate_heading_content)
}
```

**Problema**: specs es solo **declaración**, no lógica.

**Solución**: validación va en `validator.py`, no aquí.

### Antipatrón 5: Dependencias Circulares

```python
# ❌ specs.py
from lexer import tokenize

# ❌ lexer.py
from specs import TOKENS
```

**Problema**: import circular.

**Solución**: specs no debe importar nada del pipeline. Solo define datos.

### Antipatrón 6: Regex Demasiado Complejos

```python
# ❌ Regex que intenta parsear inline en el lexer
TOKENS["HEADING"] = r"^#{1,6}\s+(?P<content>(?:\*\*[\w\s]+\*\*|[\w\s]+)+)$"
```

**Problema**: mezclas tokenización de bloques con inline pass.

**Solución**: lexer captura heading completo. Inline pass es fase separada.

## [10].mvp_specs

### Mínimo Viable

Para un MVP funcional, necesitas:

**Tokens obligatorios**:
```python
BLOCK_ORDER = [
    "HEADING_ATX",   # encabezados básicos
    "BLANK_LINE",    # separador de bloques
    "TEXT"           # catch-all para párrafos
]

TOKENS = {
    "HEADING_ATX": r"^(?P<level>#{1,6})\s+(?P<content>.+)$",
    "BLANK_LINE": r"^\s*$",
    "TEXT": r"^(?P<content>.+)$"
}
```

**Nodos obligatorios**:
```python
NODES = ["document", "heading", "paragraph", "text"]

GRAMMAR = {
    "document": {"children": ["heading", "paragraph"], "meta": []},
    "heading": {"children": ["text"], "meta": ["level"]},
    "paragraph": {"children": ["text"], "meta": []},
    "text": {"children": [], "meta": ["value"]}
}
```

Con esto puedes:
- Tokenizar headings y párrafos
- Construir AST básico
- Renderizar `<h1>-<h6>` y `<p>`

### Orden de Agregar el Resto

#### Fase 1.1: HR

```python
BLOCK_ORDER.insert(2, "HR")  # después de HEADING, antes de BLANK_LINE
TOKENS["HR"] = r"^(?:---|___|\*\*\*)(?:\s*)$"
NODES.append("hr")
GRAMMAR["hr"] = {"children": [], "meta": []}
```

**Testing**: línea `---` genera nodo `hr` → renderiza `<hr>`.

#### Fase 1.2: Code Fences

```python
BLOCK_ORDER.insert(0, "CODE_FENCE_START")
BLOCK_ORDER.insert(1, "CODE_FENCE_END")

TOKENS["CODE_FENCE_START"] = r"^```(?P<lang>\w*)$"
TOKENS["CODE_FENCE_END"] = r"^```$"

NODES.append("code_block")
GRAMMAR["code_block"] = {"children": [], "meta": ["lang", "content"]}
```

**Testing**: bloque ` ```python ... ``` ` genera nodo `code_block`.

#### Fase 1.3: Listas Simples

```python
BLOCK_ORDER.insert(3, "LIST_ITEM")  # después de HR

TOKENS["LIST_ITEM"] = r"^(?P<indent>\s*)(?P<marker>[-*+])\s+(?P<content>.+)$"

NODES.extend(["list", "list_item"])
GRAMMAR["list"] = {"children": ["list_item"], "meta": ["ordered"]}
GRAMMAR["list_item"] = {"children": ["text"], "meta": []}
```

**Limitación MVP**: sin nesting (listas no anidadas).

### Criterio de "Specs MVP Completo"

Tu `specs.py` está listo para MVP cuando:

1. `BLOCK_ORDER` tiene al menos 5 tipos: `HEADING_ATX`, `HR`, `BLANK_LINE`, `TEXT`, y uno más (`CODE_FENCE` o `LIST_ITEM`)
2. Cada token en `TOKENS` usa grupos nombrados
3. `NODES` define tipos correspondientes
4. `GRAMMAR` describe estructura completa
5. Todos los regex se testean en aislamiento (pasan casos válidos/inválidos)
6. `TEXT` está al **final** de `BLOCK_ORDER`

Con esto, puedes pasar a implementar `lexer.py`.

## Conclusión

El módulo `specs` es el **contrato** entre todos los componentes del pipeline. Implementarlo correctamente desde el inicio evita refactorizaciones costosas y mantiene el sistema extensible.

**Principios clave**:

1. **Fuente única de verdad**: `BLOCK_ORDER`, `TOKENS`, `GRAMMAR` viven solo aquí.
2. **Orden importa**: específico → genérico, `TEXT` siempre al final.
3. **Grupos nombrados**: semántica explícita, robustez ante cambios.
4. **Specs = datos**: cero lógica, solo declaraciones.
5. **Extensibilidad**: agregar tokens/nodos no requiere cambiar estructura.

**Próximos pasos**:

1. Implementar MVP de `specs.py` con `HEADING_ATX`, `BLANK_LINE`, `TEXT`
2. Testear cada regex individualmente
3. Compilar `MASTER_REGEX`
4. Pasar a `lexer.py` (siguiente capítulo)

¡Recuerda!: código mínimo primero, luego iterar. No agregues `CODE_FENCE`, `LIST_ITEM`, etc. hasta que el MVP (headings + párrafos) funcione de punta a punta.
