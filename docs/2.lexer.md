# Implementación del Módulo `lexer`

## [1].motivacion

### El Rol del Lexer en el Pipeline

El lexer (o tokenizador) es el **primer paso activo** del pipeline de conversión. Mientras que `spec.py` solo define qué es válido, el lexer **aplica esas definiciones** para transformar texto crudo en una secuencia estructurada de tokens.

```text
┌──────────────┐
│  spec.py     │  ← Fuente de verdad (solo datos)
└──────┬───────┘
       ↓ consulta
┌──────────────┐
│  lexer.py    │  ← Identifica y clasifica líneas
└──────┬───────┘
       ↓ tokens
┌──────────────┐
│  parser.py   │  ← Construye AST
└──────────────┘
```

**Posición en el flujo**: el lexer recibe texto Markdown como string y produce una lista de tokens que el parser consumirá. Sin el lexer, el parser tendría que lidiar con regex, orden de precedencia y captura de grupos, violando la separación de responsabilidades.

### Beneficios de un Lexer Genérico

Un lexer **genérico** es aquel que no codifica reglas específicas de Markdown dentro de su lógica, sino que **consulta** `spec.py` para obtener patrones, orden y tipos.

#### Comparación: Lexer Hardcoded vs Genérico

**Lexer Hardcoded** (antipatrón):
```python
# ❌ lexer.py con lógica específica
def tokenize_line(line):
    if line.startswith("#"):
        level = len(line) - len(line.lstrip("#"))
        return {"type": "HEADING", "level": level}
    elif line.startswith("- "):
        return {"type": "LIST_ITEM"}
    elif line.strip() == "":
        return {"type": "BLANK"}
    else:
        return {"type": "TEXT"}
```

**Problemas**:
- Agregar un nuevo tipo (ej. `HR`) requiere modificar el código del lexer
- El orden de precedencia está enterrado en la cadena `if/elif`
- Los patrones regex están duplicados entre `spec.py` y `lexer.py`

**Lexer Genérico** (recomendado):
```python
# ✅ lexer.py consume spec.py
from spec import TOKEN_SPECS, BLOCK_FLUSH_ORDER

def tokenize_line(line):
    for token_type in BLOCK_FLUSH_ORDER:
        pattern = get_pattern(token_type)
        match = pattern.match(line)
        if match:
            return {
                "type": token_type,
                "meta": match.groupdict()
            }
```

**Ventajas**:
- Agregar un nuevo tipo solo toca `spec.py`
- El orden de precedencia viene de `BLOCK_FLUSH_ORDER`
- Cero duplicación de reglas

### ¿Por Qué Viene Justo Después de Specs?

La implementación debe seguir este orden estricto:

1. **Specs primero**: defines qué tokens existen y en qué orden se evalúan
2. **Lexer segundo**: implementas el motor genérico que consume esas definiciones
3. **Parser después**: solo cuando tienes tokens bien formados puedes agruparlos en AST

**Intentar implementar lexer antes de specs** es como escribir un intérprete antes de definir la gramática del lenguaje: te obligará a hacer suposiciones que luego tendrás que refactorizar.

## [2].responsabilidad_y_limites

### Entrada y Salida del Lexer

| Aspecto | Detalle |
|---------|---------|
| **Entrada** | String de texto Markdown completo (crudo, sin preprocesar) |
| **Salida** | Lista de tokens: `[{type, line, value, meta}, ...]` |
| **Líneas procesadas** | Todas (incluyendo líneas en blanco) |
| **Garantía** | Cada línea del input produce exactamente un token |

```text
Entrada (string):
"""
# Título

Párrafo de ejemplo.
"""

Salida (lista de dicts):
[
    {"type": "HEADING_ATX", "line": 1, "value": "# Título", "meta": {...}},
    {"type": "BLANK_LINE", "line": 2, "value": "", "meta": {}},
    {"type": "TEXT", "line": 3, "value": "Párrafo de ejemplo.", "meta": {...}}
]
```

### Qué NO Hace el Lexer

Es crucial entender los límites de responsabilidad para evitar sobrecargar el módulo.

| ❌ NO es responsabilidad del lexer | ✅ SÍ es responsabilidad del lexer |
|-------------------------------------|-------------------------------------|
| Crear nodos AST (`heading`, `paragraph`) | Identificar tipos de token (`HEADING_ATX`, `TEXT`) |
| Agrupar líneas `TEXT` en párrafos | Emitir cada línea `TEXT` como token individual |
| Validar que un heading no esté dentro de una lista | Capturar el nivel del heading en `meta` |
| Decidir si un `TEXT` es parte de un código o un párrafo | Mantener estado simple (ej. `dentro_fence`) |
| Procesar inline pass (énfasis, enlaces) | Capturar contenido crudo de líneas |
| Lanzar errores por tokens "inválidos" | Emitir token para cada línea (tolerancia total) |

### Punto de Corte con Parser

**Lexer termina cuando**: cada línea tiene su token con tipo identificado y metadatos extraídos.

**Parser empieza cuando**: recibe la lista completa de tokens y debe decidir cómo agruparlos.

Ejemplo de frontera:
```markdown
Este es un párrafo
que continúa en múltiples
líneas.
```

**Lexer produce**:
```python
[
    {"type": "TEXT", "line": 1, "meta": {"content": "Este es un párrafo"}},
    {"type": "TEXT", "line": 2, "meta": {"content": "que continúa en múltiples"}},
    {"type": "TEXT", "line": 3, "meta": {"content": "líneas."}}
]
```

**Parser consume** esos tres tokens y crea:
```python
{
    "type": "paragraph",
    "children": [
        {"type": "text", "value": "Este es un párrafo que continúa en múltiples líneas."}
    ]
}
```

**Regla de oro**: el lexer **identifica**, el parser **agrupa**, el validator **verifica**.

### Punto de Corte con Validator

El lexer **no valida semántica**. Ejemplos de lo que NO debe hacer:

- ❌ Rechazar headings de nivel 7 (`####### Inválido`)
  - **Decisión**: el lexer lo tokeniza como `TEXT` (porque el regex de `HEADING_ATX` en specs solo acepta 1-6). El validator luego puede reportar si es necesario.

- ❌ Validar que un code fence tenga cierre
  - **Decisión**: el lexer emite `CODE_FENCE_START` y, si existe, `CODE_FENCE_END`. El parser detecta fences sin cerrar; el validator lo reporta.

- ❌ Verificar que una lista tenga indentación consistente
  - **Decisión**: el lexer captura el `indent` en `meta`. El validator aplica reglas de consistencia.

**Principio**: el lexer confía en que los patrones de `spec.py` definen qué es "válido sintácticamente". Si algo no matchea ningún patrón específico, cae en `TEXT` (catch-all).

## [3].flujo_general_de_tokenizacion

### Proceso Línea por Línea

El lexer procesa texto Markdown dividiendo por líneas y evaluando cada una de forma independiente (salvo estados simples como code fences).

```text
función tokenize(text_markdown):
    tokens ← []
    líneas ← text_markdown.splitlines()
    
    para cada (índice, línea) en enumerar(líneas):
        número_línea ← índice + 1  # 1-indexed para humanos
        token ← identificar_token(línea, número_línea)
        tokens.append(token)
    
    retornar tokens
```

**Decisión clave**: usar `splitlines()` en lugar de `split("\n")` para manejar correctamente diferentes finales de línea (`\n`, `\r\n`, `\r`).

**Numeración 1-indexed**: las líneas se numeran desde 1 para que los mensajes de error sean intuitivos ("error en línea 5" es más natural que "error en índice 4").

### Estrategias de Matching

Hay dos enfoques principales para identificar el tipo de token de cada línea:

#### Opción A: Iterar sobre Tokens Compilados

```text
función identificar_token(línea, número):
    # COMPILED_TOKENS = [(tipo, regex_compilado), ...]
    # Ordenados según BLOCK_FLUSH_ORDER
    
    para cada (tipo, patrón) en COMPILED_TOKENS:
        match ← patrón.match(línea)
        si match:
            retornar construir_token(tipo, número, línea, match)
    
    # Si llegamos aquí, ningún patrón matcheó (error de configuración en spec.py)
    # El lexer NO debe fallar: emitir token fallback
    retornar {
        "type": "TEXT",  # o "UNKNOWN" para marcarlo explícitamente
        "line": número,
        "value": línea,
        "meta": {"content": línea}
    }
```

**Ventajas**:
- Explícito: ves claramente qué patrón está probando
- Fácil de debuggear: puedes loggear cada intento
- Flexible: puedes inyectar lógica especial entre patrones

**Desventajas**:
- Más código: necesitas iterar manualmente
- Ligeramente más lento (pero despreciable para archivos pequeños)

#### Opción B: Usar MASTER_REGEX Unificado

```text
función identificar_token(línea, número):
    # MASTER_REGEX = regex único que combina todos los patrones
    # Cada patrón está en un grupo nombrado por tipo
    
    match ← MASTER_REGEX.match(línea)
    
    si match:
        tipo ← match.lastgroup  # nombre del grupo que matcheó
        retornar construir_token(tipo, número, línea, match)
    
    # Fallback: emitir token genérico en lugar de lanzar error
    retornar {
        "type": "TEXT",
        "line": número,
        "value": línea,
        "meta": {"content": línea}
    }
```

**Ventajas**:
- Muy eficiente: una sola operación de match
- Compacto: menos líneas de código
- El orden ya está codificado en el regex unificado

**Desventajas**:
- Menos control: no puedes inyectar lógica entre patrones
- Debugging más difícil: el regex combinado es complejo de inspeccionar

**Recomendación para MVP**: usar **Opción A** (iterar sobre `COMPILED_TOKENS`) para claridad durante desarrollo. Optimizar a Opción B solo si hay problemas de performance.

### Pseudocódigo del Bucle Principal

```text
función tokenize(text):
    tokens ← lista_vacía()
    líneas ← text.splitlines()
    estado ← inicializar_estado()  # para code fences, etc.
    
    para cada (idx, línea) en enumerar(líneas):
        número_línea ← idx + 1
        
        # Caso especial: detectar blank line antes de regex
        si línea.strip() == "":
            token ← crear_token_blank(número_línea, línea)
            tokens.append(token)
            continuar
        
        # Matching normal
        token ← identificar_tipo(línea, número_línea, estado)
        
        # Actualizar estado si es necesario (code fences)
        actualizar_estado(token, estado)
        
        tokens.append(token)
    
    retornar tokens

función identificar_tipo(línea, número, estado):
    # Iterar sobre patrones en orden de BLOCK_FLUSH_ORDER
    para cada (tipo, patrón) en COMPILED_TOKENS:
        match ← patrón.match(línea)
        si match:
            meta ← match.groupdict()
            retornar {
                "type": tipo,
                "line": número,
                "value": línea,
                "meta": meta
            }
    
    # Fallback: error de configuración en spec.py (TEXT debería estar al final)
    # El lexer es tolerante: emite token genérico para que el validator lo reporte
    retornar {
        "type": "TEXT",  # o "UNKNOWN" si prefieres marcarlo explícitamente
        "line": número,
        "value": línea,
        "meta": {"content": línea}
    }
```

**Nota sobre estado**: se introduce aquí conceptualmente pero se detalla en la sección [7].

### Primera Coincidencia Gana

El orden en `BLOCK_FLUSH_ORDER` (o como esté nombrado en tu `spec.py`) es **crítico** porque implementa la regla de "primera coincidencia gana".

```text
Ejemplo con BLOCK_FLUSH_ORDER = ["HEADING_ATX", "HR", "TEXT"]:

Línea: "# Introducción"
1. Probar HEADING_ATX: ✓ match → retornar token HEADING_ATX
   (no se prueban HR ni TEXT)

Línea: "---"
1. Probar HEADING_ATX: ✗ no match
2. Probar HR: ✓ match → retornar token HR
   (no se prueba TEXT)

Línea: "Un párrafo normal"
1. Probar HEADING_ATX: ✗ no match
2. Probar HR: ✗ no match
3. Probar TEXT: ✓ match → retornar token TEXT
```

**Consecuencia**: si `TEXT` estuviera al principio, capturaría todas las líneas y nunca se evaluarían los patrones específicos.

## [4].formato_de_token_y_metadatos

### Estructura Canónica de un Token

Cada token emitido por el lexer debe tener esta estructura:

```python
{
    "type": str,      # Tipo de token (debe estar en spec.py)
    "line": int,      # Número de línea (1-indexed)
    "value": str,     # Contenido original de la línea (para debugging)
    "meta": dict      # Datos extraídos por grupos nombrados del regex
}
```

**Justificación de cada campo**:

| Campo | Por qué es necesario |
|-------|----------------------|
| `type` | El parser necesita saber qué tipo de construcción es |
| `line` | Para mensajes de error precisos en validator/renderer |
| `value` | Debugging: ver línea original sin procesar |
| `meta` | Datos específicos del tipo (nivel de heading, contenido, etc.) |

### Meta como Dict Construido desde match.groupdict()

El objeto `match` de Python (resultado de `regex.match()`) tiene un método `groupdict()` que retorna un diccionario con todos los grupos nombrados capturados.

```python
import re

# Regex con grupos nombrados
pattern = re.compile(r"^(?P<level>#{1,6})\s+(?P<content>.+)$")
match = pattern.match("## Introducción")

# Extraer meta automáticamente
meta = match.groupdict()
# Resultado: {"level": "##", "content": "Introducción"}
```

**Ventaja**: no necesitas extraer grupos manualmente por índice o nombre; `groupdict()` lo hace genéricamente.

**Construcción del token**:
```text
función construir_token(tipo, número, línea, match):
    retornar {
        "type": tipo,
        "line": número,
        "value": línea,
        "meta": match.groupdict()
    }
```

### Conservar value Original para Debugging

Aunque `meta["content"]` contenga el texto procesado, `value` guarda la línea completa sin modificar.

**Ejemplo**:
```markdown
##    Título con   espacios raros
```

Token generado:
```python
{
    "type": "HEADING_ATX",
    "line": 1,
    "value": "##    Título con   espacios raros",  # original
    "meta": {
        "level": "##",
        "content": "Título con   espacios raros"
    }
}
```

Más adelante, si el parser normaliza espacios (`"Título con espacios raros"`), puedes comparar con `value` para debugging.

### Mini-Ejemplo: 3 Líneas → 3 Tokens

**Entrada**:
```markdown
# Bienvenida

Este es el primer párrafo.
```

**Salida esperada del lexer**:
```python
[
    {
        "type": "HEADING_ATX",
        "line": 1,
        "value": "# Bienvenida",
        "meta": {
            "level": "#",
            "content": "Bienvenida"
        }
    },
    {
        "type": "BLANK_LINE",
        "line": 2,
        "value": "",
        "meta": {}
    },
    {
        "type": "TEXT",
        "line": 3,
        "value": "Este es el primer párrafo.",
        "meta": {
            "content": "Este es el primer párrafo."
        }
    }
]
```

**Observaciones**:
- `BLANK_LINE` tiene `meta` vacío (no hay datos que capturar)
- `level` contiene los símbolos `#` literales; el parser convertirá a número
- `value` preserva la línea exacta

## [5].deteccion_de_lineas_en_blanco

### ¿Debe BLANK_LINE Estar en spec.py?

Hay dos enfoques válidos:

#### Opción A: BLANK_LINE Definido en spec.py

```python
# En spec.py
TOKEN_SPECS = [
    # ...
    ("BLANK_LINE", r"^\s*$"),
    # ...
]
```

**Ventajas**:
- Consistente: todos los tipos de token en el mismo lugar
- Regex explícito: puedes ajustar qué cuenta como "blanco" (solo espacios, tabs, etc.)

**Desventajas**:
- Overhead: evaluar regex para algo que puede detectarse con `line.strip() == ""`

#### Opción B: Manejo Directo en lexer.py (Recomendado para MVP)

```text
función tokenize(text):
    tokens ← []
    líneas ← text.splitlines()
    
    para cada (idx, línea) en enumerar(líneas):
        número ← idx + 1
        
        # Detección directa antes de evaluar regex
        si línea.strip() == "":
            tokens.append({
                "type": "BLANK_LINE",
                "line": número,
                "value": línea,  # puede ser "", " ", "\t", etc.
                "meta": {}
            })
            continuar  # saltar evaluación de regex
        
        # Matching normal para líneas no-blancas
        token ← identificar_tipo(línea, número)
        tokens.append(token)
```

**Ventajas**:
- Eficiente: evita compilar/evaluar regex para caso trivial
- Claro: el manejo de blank lines es visible en el flujo principal

**Decisión para MVP**: usar **Opción B** (detección directa) para simplificar. Si más adelante necesitas personalizar qué cuenta como "blanco", mueve el patrón a `spec.py`.

### Regla Simple de Detección

```python
# Línea en blanco: vacía o solo whitespace
def es_linea_blanca(linea):
    return linea.strip() == ""

# Casos que matchean:
# - ""         → True
# - "   "      → True
# - "\t\t"     → True
# - " \n "     → True (después de strip)

# Casos que NO matchean:
# - " a "      → False
# - "\t#"      → False
```

**Importante**: `strip()` elimina espacios, tabs, saltos de línea y otros caracteres de whitespace. Esto cubre todos los casos típicos de líneas "vacías".

### Efecto en el Parser

Las líneas en blanco tienen un rol semántico crucial: **separan bloques**.

**Ejemplo sin blank line**:
```markdown
Este es un párrafo
que continúa.
```
→ Parser agrupa en **un solo** nodo `paragraph`

**Ejemplo con blank line**:
```markdown
Este es un párrafo.

Este es otro párrafo.
```
→ Parser crea **dos** nodos `paragraph` separados

**Token stream correspondiente**:
```python
[
    {"type": "TEXT", "line": 1, ...},
    {"type": "BLANK_LINE", "line": 2, ...},  # señal de separación
    {"type": "TEXT", "line": 3, ...}
]
```

El parser usa `BLANK_LINE` como **señal de flush**: cuando lo encuentra, debe finalizar el buffer de párrafo actual y empezar uno nuevo.

### Caso Especial: Múltiples Blank Lines Consecutivas

```markdown
Párrafo 1.


Párrafo 2.
```

**Token stream**:
```python
[
    {"type": "TEXT", "line": 1, ...},
    {"type": "BLANK_LINE", "line": 2, ...},
    {"type": "BLANK_LINE", "line": 3, ...},  # segunda línea blanca
    {"type": "TEXT", "line": 4, ...}
]
```

**Decisión de diseño**: el lexer emite **todos** los tokens `BLANK_LINE`. El parser puede:
- Ignorar blank lines adicionales después de la primera (comportamiento típico)
- O contarlas para validación de estilo (ej. "máximo 1 línea blanca entre bloques")

**Recomendación MVP**: el lexer emite todos; el parser ignora blank lines consecutivos (los trata como uno solo).

## [6].consumo_de_specs_y_orden_de_coincidencia

### Cómo Usar BLOCK_FLUSH_ORDER para Precedencia

El lexer **no debe** contener lógica de precedencia hardcoded. En su lugar, consulta `BLOCK_FLUSH_ORDER` (o el nombre que uses en `spec.py`) como fuente única de verdad.

**Ejemplo de spec.py**:
```python
BLOCK_FLUSH_ORDER = [
    "CODE_FENCE_START",
    "CODE_FENCE_END",
    "HEADING_ATX",
    "HR",
    "LIST_ITEM",
    "TEXT"
]

TOKEN_SPECS = [
    ("CODE_FENCE_START", r"^```(?P<lang>\w*)$"),
    ("CODE_FENCE_END", r"^```$"),
    ("HEADING_ATX", r"^(?P<level>#{1,6})\s+(?P<content>.+)$"),
    ("HR", r"^(?:---|___|\*\*\*)$"),
    ("LIST_ITEM", r"^(?P<indent>\s*)[-*+]\s+(?P<content>.+)$"),
    ("TEXT", r"^(?P<content>.+)$")
]
```

**Lexer consume el orden**:
```text
función compilar_tokens():
    # Compilar patrones en el orden especificado
    compilados ← []
    para cada tipo en BLOCK_FLUSH_ORDER:
        regex ← buscar_en_TOKEN_SPECS(tipo)
        patrón_compilado ← re.compile(regex)
        compilados.append((tipo, patrón_compilado))
    retornar compilados

# Resultado: COMPILED_TOKENS en orden de precedencia
COMPILED_TOKENS = compilar_tokens()
```

**Ventaja**: cambiar el orden en `spec.py` (ej. poner `HR` antes de `HEADING_ATX`) afecta automáticamente al lexer sin tocar su código.

### Demostración de Casos Frontera

#### Caso 1: TEXT Siempre al Final

```python
# ❌ Orden incorrecto
BLOCK_FLUSH_ORDER = ["TEXT", "HEADING_ATX", "HR"]

# Línea: "# Hola"
# 1. Probar TEXT (^.+) → ✓ match → retorna TEXT
# 2. HEADING_ATX nunca se evalúa ❌
```

**Problema**: `TEXT` con regex `^.+` captura cualquier línea no vacía, incluyendo headings y HRs.

**Solución**: `TEXT` siempre al **final**.

```python
# ✅ Orden correcto
BLOCK_FLUSH_ORDER = ["HEADING_ATX", "HR", "TEXT"]

# Línea: "# Hola"
# 1. Probar HEADING_ATX → ✓ match → retorna HEADING_ATX ✓
```

#### Caso 2: HR Antes de TEXT

```markdown
---
```

```python
# ✅ Orden correcto
BLOCK_FLUSH_ORDER = ["HR", "TEXT"]

# Línea: "---"
# 1. Probar HR (^---$) → ✓ match → retorna HR ✓
```

Si `TEXT` estuviera primero, la línea `---` sería tokenizada como `TEXT` en lugar de `HR`.

#### Caso 3: Code Fences Antes de TODO

```markdown
```python
código
```
```

Los code fences deben tener **máxima prioridad** porque una línea ` ``` ` podría confundirse con `TEXT`.

```python
# ✅ Orden correcto
BLOCK_FLUSH_ORDER = [
    "CODE_FENCE_START",  # prioridad 0
    "CODE_FENCE_END",    # prioridad 1
    "HEADING_ATX",       # prioridad 2
    # ...
    "TEXT"               # última prioridad
]
```

### Uso de MASTER_REGEX: match.lastgroup

Si decides usar un regex maestro unificado:

```text
función compilar_master_regex():
    patrones ← []
    para cada tipo en BLOCK_FLUSH_ORDER:
        regex ← buscar_en_TOKEN_SPECS(tipo)
        # Envolver en grupo nombrado
        patrón_envuelto ← f"(?P<{tipo}>{regex})"
        patrones.append(patrón_envuelto)
    
    # Unir con alternancia |
    regex_combinado ← "|".join(patrones)
    retornar re.compile(regex_combinado)

MASTER_REGEX = compilar_master_regex()
```

**Uso en lexer**:
```text
función identificar_tipo(línea):
    match ← MASTER_REGEX.match(línea)
    si match:
        tipo ← match.lastgroup  # nombre del grupo que matcheó
        meta ← match.groupdict()
        retornar {"type": tipo, "meta": meta}
```

**Ventaja**: `lastgroup` te dice automáticamente cuál patrón matcheó primero, respetando el orden de `BLOCK_FLUSH_ORDER`.

### Iteración vs MASTER_REGEX: Tabla Comparativa

| Aspecto | Iterar COMPILED_TOKENS | MASTER_REGEX |
|---------|------------------------|--------------|
| **Performance** | Ligeramente más lento (evalúa patrones secuencialmente) | Más rápido (una sola operación de match) |
| **Claridad** | Explícito: ves cada intento de match | Implícito: lógica en regex combinado |
| **Debugging** | Fácil: loggear cada patrón probado | Difícil: regex unificado es complejo |
| **Flexibilidad** | Puedes inyectar lógica especial entre patrones | Todo o nada |
| **Recomendación** | ✅ Para MVP y desarrollo | Para optimización posterior |

## [7].manejo_de_estado_basico

### Estados Mínimos: Code Fences

La mayoría de los tokens Markdown son **independientes** (una línea de heading no afecta la siguiente). Sin embargo, los **code fences** requieren estado porque delimitan un bloque multi-línea.

```markdown
```python
def hola():
    return "mundo"
```
```

**Problema**: las líneas interiores (`def hola():`, etc.) técnicamente podrían matchear `TEXT`, pero semánticamente pertenecen al bloque de código.

### Campos opens_state y closes_state en spec.py

Una forma declarativa de manejar esto es agregar metadata a los tokens en `spec.py`:

```python
TOKEN_SPECS = [
    ("CODE_FENCE_START", r"^```(?P<lang>\w*)$", {"opens_state": "code"}),
    ("CODE_FENCE_END", r"^```$", {"closes_state": "code"}),
    # ...
]
```

**Interpretación**:
- `opens_state: "code"` → cuando el lexer ve este token, entra en estado `"code"`
- `closes_state: "code"` → cuando ve este token, sale del estado `"code"`

### Pseudocódigo: Manejo de Estado en Lexer

```text
función tokenize(text):
    tokens ← []
    líneas ← text.splitlines()
    estado_actual ← None  # puede ser None, "code", etc.
    
    para cada (idx, línea) en enumerar(líneas):
        número ← idx + 1
        
        # Detección de blank line (sin importar estado)
        si línea.strip() == "":
            tokens.append(crear_token_blank(número, línea))
            continuar
        
        # Lógica dependiente de estado
        si estado_actual == "code":
            # Estamos dentro de un code fence
            # ¿Es la línea de cierre?
            si coincide_con_CODE_FENCE_END(línea):
                token ← crear_token("CODE_FENCE_END", número, línea)
                tokens.append(token)
                estado_actual ← None  # cerrar estado
            sino:
                # Línea interior del code fence
                # Opción 1: emitir como TEXT genérico
                token ← crear_token("TEXT", número, línea, {"dentro_fence": True})
                tokens.append(token)
                # El parser agrupará estos TEXT con el fence
        sino:
            # Estado normal (fuera de fences)
            token ← identificar_tipo(línea, número)
            
            # ¿Este token abre un estado?
            si token.type == "CODE_FENCE_START":
                estado_actual ← "code"
            
            tokens.append(token)
    
    retornar tokens
```

### Límite: ¿El Lexer Agrupa o Solo Marca?

Hay dos filosofías:

#### Opción A: Lexer Solo Marca (Recomendado)

El lexer emite tokens individuales para cada línea, incluso dentro del fence:

```python
# Token stream:
[
    {"type": "CODE_FENCE_START", "line": 1, "meta": {"lang": "python"}},
    {"type": "TEXT", "line": 2, "meta": {"content": "def hola():", "dentro_fence": True}},
    {"type": "TEXT", "line": 3, "meta": {"content": "    return \"mundo\"", "dentro_fence": True}},
    {"type": "CODE_FENCE_END", "line": 4, "meta": {}}
]
```

**Ventaja**: el lexer sigue siendo simple (solo identifica líneas). El parser agrupa el bloque.

#### Opción B: Lexer Agrupa Directamente

El lexer acumula líneas interiores y emite un único token con todo el contenido:

```python
# Token stream:
[
    {"type": "CODE_BLOCK", "line": 1, "meta": {
        "lang": "python",
        "content": "def hola():\n    return \"mundo\"",
        "end_line": 4
    }}
]
```

**Ventaja**: el parser recibe bloques ya formados.  
**Desventaja**: el lexer pierde simplicidad; mezcla identificación con agrupación.

**Recomendación MVP**: usar **Opción A** (lexer solo marca). Mantiene separación de responsabilidades.

### Aclaración: Estado vs Agrupación

- **Estado** en el lexer: bandera simple (`dentro_fence`, `dentro_lista`) que afecta cómo se identifican líneas
- **Agrupación**: combinar múltiples tokens en un nodo AST (responsabilidad del **parser**)

**Ejemplo**:
- Lexer con estado: "Esta línea está dentro de un fence, así que aunque parezca heading, la marco como TEXT"
- Parser sin estado: "Veo CODE_FENCE_START seguido de varios TEXT seguido de CODE_FENCE_END → creo nodo code_block"

El estado del lexer es **mínimo y local** (solo afecta la identificación del tipo). La agrupación es **global y estructural** (crea jerarquías).

## [8].extraccion_y_normalizacion_de_meta

### Meta = match.groupdict()

Como se mencionó en la sección [4], la forma más directa de extraer metadatos es usar `groupdict()`:

```python
pattern = re.compile(r"^(?P<level>#{1,6})\s+(?P<content>.+)$")
match = pattern.match("### Título")

meta = match.groupdict()
# {"level": "###", "content": "Título"}
```

**Sin normalización**, `meta` contiene strings crudos tal como los capturó el regex.

### Normalizaciones Sugeridas

Algunas transformaciones son útiles hacerlas **en el lexer** para no duplicarlas en el parser.

#### Normalización 1: Nivel de Heading como Entero

```python
# Regex captura: "###" (string)
# Normalizar a: 3 (int)

meta = match.groupdict()
if "level" in meta:
    meta["level"] = len(meta["level"])  # contar símbolos #
```

**Ejemplo**:
```python
# Antes: {"level": "###", "content": "Título"}
# Después: {"level": 3, "content": "Título"}
```

**Justificación**: el parser y renderer usan el número, no los símbolos. Convertir aquí evita repetir la lógica.

#### Normalización 2: Contenido Trimmed

```python
# Regex captura: "  Título con espacios  " (con espacios extra)
# Normalizar a: "Título con espacios"

meta = match.groupdict()
if "content" in meta:
    meta["content"] = meta["content"].strip()
```

**Justificación**: Markdown es tolerante a espacios extra. Normalizarlos en el lexer simplifica el parser.

#### Normalización 3: Indent como Número

Para listas, el regex captura el indent como string de espacios/tabs:

```python
# Regex: r"^(?P<indent>\s*)[-*+]\s+(?P<content>.+)$"
# Captura: "    " (4 espacios) o "\t" (1 tab)

meta = match.groupdict()
if "indent" in meta:
    # Convertir tabs a espacios (asumiendo 1 tab = 2 espacios, ajustar según política)
    indent_str = meta["indent"].replace("\t", "  ")
    meta["indent"] = len(indent_str)  # número de espacios
```

**Ejemplo**:
```python
# Antes: {"indent": "    ", "content": "Item"}
# Después: {"indent": 4, "content": "Item"}
```

**Justificación**: el parser necesita el nivel de indent numérico para detectar nesting.

### Cuándo NO Normalizar en el Lexer

**Regla**: no normalices si la decisión depende de **contexto** o **políticas complejas**.

**Ejemplos de normalizaciones que van en el parser o validator**:

- ❌ Unir múltiples líneas `TEXT` en un párrafo → **parser** (requiere contexto de líneas siguientes)
- ❌ Validar que el nivel de heading no salte (de h1 a h3) → **validator** (requiere contexto de nodos previos)
- ❌ Procesar inline pass (convertir `*cursiva*` en nodo `emphasis`) → **módulo inline** (fase separada)

**Normalizaciones apropiadas en el lexer**:
- ✅ Convertir strings capturados a tipos útiles (int, bool)
- ✅ Eliminar whitespace irrelevante (strip, trim)
- ✅ Aplicar políticas simples definidas en `spec.py` (ej. tabs a espacios)

### Registrar Decisiones de Normalización

**Importante**: documenta en comentarios qué normalizaciones hace el lexer para evitar duplicación.

```python
def construir_token(tipo, numero, linea, match):
    meta = match.groupdict()
    
    # Normalizaciones aplicadas en lexer:
    if tipo == "HEADING_ATX":
        # Conversión: símbolos # → número entero
        meta["level"] = len(meta["level"])
        # Trim: eliminar espacios extra del contenido
        meta["content"] = meta["content"].strip()
    
    elif tipo == "LIST_ITEM":
        # Conversión: indent string → número de espacios
        indent_str = meta["indent"].replace("\t", "  ")  # política: 1 tab = 2 espacios
        meta["indent"] = len(indent_str)
        meta["content"] = meta["content"].strip()
    
    return {
        "type": tipo,
        "line": numero,
        "value": linea,  # original sin normalizar
        "meta": meta
    }
```

**Beneficio**: si el parser encuentra `meta["level"]`, sabe que ya es un int, no un string.

## [9].errores_y_debug_minimo

### Qué Hacer Si Ninguna Regex Coincide

En teoría, si `TEXT` está al final con regex `^.+$`, **toda línea no-blanca** debería matchear. Si llegas a un estado donde ningún patrón coincide, es un **error de configuración en `spec.py`**, no un error del input Markdown.

```text
función identificar_tipo(línea, número):
    para cada (tipo, patrón) en COMPILED_TOKENS:
        match ← patrón.match(línea)
        si match:
            retornar construir_token(tipo, número, línea, match)
    
    # No debería llegar aquí si TEXT está configurado correctamente
    # IMPORTANTE: el lexer NO lanza errores, es tolerante
    retornar {
        "type": "TEXT",  # o "UNKNOWN" para marcarlo
        "line": número,
        "value": línea,
        "meta": {"content": línea}
    }
```

**Posibles causas** de que llegues al fallback:
1. `TEXT` no está en `BLOCK_FLUSH_ORDER`
2. El regex de `TEXT` es demasiado restrictivo (ej. `^[a-z]+$` solo letras)
3. Hay un bug en la compilación de patrones

**Filosofía del fallback**: el lexer es **tolerante** y nunca falla. Si algo está mal configurado, emite un token genérico (`TEXT` o `UNKNOWN`) y deja que el **validator** lo reporte como problema.

| Situación | Lexer (tolerante) | Validator (estricto) |
|-----------|-------------------|----------------------|
| Línea `####### H7` (7 símbolos) | ✅ Emite token `TEXT` | ⚠️ "Parece heading inválido" |
| Specs sin `TEXT` al final | ✅ Emite token `TEXT` fallback | ❌ "Error de configuración" |
| Code fence sin cerrar | ✅ Emite todos los tokens | ❌ "Fence sin cerrar" |

**Nunca hagas esto en el lexer**:
```python
# ❌ MAL: lanzar excepción
if not match:
    raise ValueError(f"Línea {numero} no es Markdown válido")
```

**Siempre haz esto**:
```python
# ✅ BIEN: emitir token fallback
if not match:
    return {"type": "TEXT", "line": numero, "value": linea, "meta": {"content": linea}}
```

## [10].mvp_lexer_y_plan_de_ampliacion

### MVP: Soporte Mínimo

Para validar que el lexer funciona de punta a punta, empieza con **tres tipos de token**:

```python
# spec.py (MVP)
BLOCK_FLUSH_ORDER = [
    "HEADING_ATX",
    "BLANK_LINE",
    "TEXT"
]

TOKEN_SPECS = [
    ("HEADING_ATX", r"^(?P<level>#{1,6})\s+(?P<content>.+)$"),
    ("BLANK_LINE", r"^\s*$"),  # opcional si manejas directo en lexer
    ("TEXT", r"^(?P<content>.+)$")
]
```

### Pseudocódigo del Bucle Principal MVP

```text
import re

# Compilar patrones una vez
función compilar_tokens():
    resultado ← []
    para cada (tipo, regex) en TOKEN_SPECS:
        si tipo está en BLOCK_FLUSH_ORDER:
            resultado.append((tipo, re.compile(regex)))
    retornar resultado

COMPILED_TOKENS = compilar_tokens()

# Función principal de tokenización
función tokenize(text):
    tokens ← []
    líneas ← text.splitlines()
    
    para cada (idx, línea) en enumerar(líneas):
        número_línea ← idx + 1
        
        # Caso especial: blank line
        si línea.strip() == "":
            tokens.append({
                "type": "BLANK_LINE",
                "line": número_línea,
                "value": línea,
                "meta": {}
            })
            continuar
        
        # Matching normal
        para cada (tipo, patrón) en COMPILED_TOKENS:
            match ← patrón.match(línea)
            si match:
                meta ← match.groupdict()
                
                # Normalización MVP
                si tipo == "HEADING_ATX":
                    meta["level"] = len(meta["level"])
                    meta["content"] = meta["content"].strip()
                
                tokens.append({
                    "type": tipo,
                    "line": número_línea,
                    "value": línea,
                    "meta": meta
                })
                romper  # primera coincidencia gana
    
    retornar tokens
```

## Conclusión

El módulo `lexer` es el **motor de identificación** del pipeline. Su diseño genérico (consumir `spec.py` en lugar de hardcodear reglas) lo hace extensible y mantenible.

**Principios clave**:

1. **Solo reconoce**: no valida, no agrupa, no transforma (solo normaliza metadatos simples)
2. **Fuente única**: precedencia viene de `BLOCK_FLUSH_ORDER` en `spec.py`
3. **Estructura uniforme**: todos los tokens tienen `{type, line, value, meta}`
4. **Estado mínimo**: solo para casos especiales como code fences
5. **TEXT al final**: garantiza que no haya líneas sin matchear

**Próximos pasos**:

1. Implementar MVP del lexer con `HEADING_ATX`, `BLANK_LINE`, `TEXT`
2. Crear tests de tokenización para casos básicos
3. Validar que los tokens producidos sean correctos antes de pasar al parser
4. Ampliar iterativamente: HR → CODE_FENCE → LIST_ITEM

Recuerda: el lexer debe ser **tonto** (no toma decisiones semánticas). Su único trabajo es decir "esta línea es de tipo X y tiene estos datos Y". El parser es quien construye significado a partir de la secuencia de tokens.
