# Introducción: Markdown → HTML vía AST (sin POO)

## [1].introduccion_general

### Propósito del Proyecto

Este proyecto implementa un **conversor de Markdown a HTML** mediante un pipeline basado en **Abstract Syntax Tree (AST)**, utilizando exclusivamente **funciones y módulos** (sin programación orientada a objetos).

**¿Por qué AST?**

- **Separación de responsabilidades**: tokenización, parsing, validación y renderizado son fases independientes y testeables por separado.
- **Extensibilidad**: agregar nuevas construcciones Markdown no requiere reescribir el pipeline completo, solo ajustar specs y añadir reglas.
- **Validación profunda**: un AST permite validar reglas contextuales (ej. "no encabezados dentro de listas") de forma declarativa, sin contaminar el parser.
- **Múltiples outputs**: el mismo AST puede renderizarse a HTML, JSON, texto plano o cualquier formato objetivo.

### Alcance Inicial (MVP, Minimum Viable Product)

Implementaremos un **subset reducido** de Markdown:

- **Headings ATX** (`#` a `######`)
- **Párrafos** (bloques de texto continuos)
- **Líneas en blanco** (separadores de bloques)
- **Listas no anidadas** (sin nesting en v1)
- **Code fences** (bloques de código delimitados por ` ``` `)
- **Regla horizontal** (`---`, `***`)
- **Énfasis básico** (`*cursiva*`, `**negrita**` — inline pass en fase 2)

Esto permite validar la arquitectura completa antes de agregar complejidad (tablas, listas anidadas, Setext headings, imágenes, etc.).

### ¿Por qué Solo Funciones y Módulos?

- **Simplicidad**: evitamos la sobrecarga conceptual de clases, herencia y estado mutable.
- **Composición explícita**: las funciones reciben datos, retornan datos; el flujo es lineal y predecible.
- **Facilidad de testing**: cada función es una caja negra testeable con entradas/salidas claras.
- **Menos tentaciones de acoplamiento**: POO tiende a crear jerarquías complejas; funciones fuerzan diseño plano.

## [2].arquitectura

### Diagrama de Flujo

```text
┌─────────────┐
│    specs    │  ← Fuente de verdad: regex, orden, gramática
└──────┬──────┘
       ↓
┌─────────────┐
│    lexer    │  ← Texto → lista de tokens
└──────┬──────┘
       ↓
┌─────────────┐
│    parser   │  ← Tokens → AST (árbol de nodos)
└──────┬──────┘
       ↓
┌─────────────┐
│  validator  │  ← Recorre AST, aplica reglas contextuales
└──────┬──────┘
       ↓
┌─────────────┐
│  renderer   │  ← AST → HTML (con escape seguro)
└─────────────┘
```

### Flujo de Datos

| Entrada | Módulo | Salida |
|---------|--------|--------|
| Texto crudo | `lexer.tokenize(text)` | `[{type, line, meta}, ...]` |
| Lista de tokens | `parser.parse(tokens)` | `{type: "document", children: [...]}` |
| AST | `validator.validate(ast)` | AST + lista de errores/warnings |
| AST válido | `renderer.to_html(ast)` | String HTML |

### Separación de Responsabilidades

- **specs**: solo **datos** (regex, orden, políticas). Cero lógica.
- **lexer**: solo **identificación** de tokens línea por línea.
- **parser**: solo **construcción** de nodos (AST).
- **validator**: solo **verificación** de reglas sobre AST ya construido.
- **renderer**: solo **conversión** de nodos a HTML con escape seguro.

**Regla de oro**: cada módulo ignora los detalles internos de los demás. Comunicación vía estructuras de datos simples (dicts, lists).

## [3].specs

### Descripción Breve

Define **qué es válido** en nuestro lenguaje Markdown: tipos de tokens, patrones regex, orden de prioridad, tipos de nodos AST y gramática base. **No contiene lógica de ejecución**, solo declaraciones.

### Contenido Mínimo Indispensable

#### 3.1. `BLOCK_ORDER` (fuente única de verdad para prioridades)

Lista ordenada de tipos de token. El lexer prueba patrones en este orden exacto.

```python
BLOCK_ORDER = [
    "CODE_FENCE_START",
    "CODE_FENCE_END",
    "HEADING_ATX",
    "HR",
    "LIST_ITEM",
    "BLANK_LINE",
    "TEXT",  # catch-all al final
]
```

**Criterio**: patrones específicos primero, catch-all al final. No duplicar orden en diccionarios separados.

#### 3.2. `TOKENS` (regex con grupos nombrados)

Diccionario de patrones. Cada regex debe capturar grupos útiles para el parser.

```python
TOKENS = {
    "HEADING_ATX": r"^(?P<level>#{1,6})\s+(?P<content>.+)$",
    "BLANK_LINE": r"^\s*$",
    "HR": r"^(?:---|\*\*\*|___)\s*$",
    "CODE_FENCE_START": r"^```(?P<lang>\w*)$",
    "CODE_FENCE_END": r"^```$",
    "LIST_ITEM": r"^(?P<indent>\s*)[-*+]\s+(?P<content>.+)$",
    "TEXT": r"^(?P<content>.+)$",  # último recurso
}
```

**No hacer**: diccionarios espejo `{"HEADING_ATX": "HEADING_ATX"}` sin funcionalidad clara. Si necesitas un "enum", usa las claves directamente o constantes simples.

#### 3.3. `NODES` (tipos canónicos de AST)

Lista simple de tipos de nodos. Puede ser un conjunto de strings.

```python
NODES = {
    "document",
    "heading",
    "paragraph",
    "list",
    "list_item",
    "code_block",
    "hr",
    "text",  # nodo hoja
}
```

#### 3.4. `GRAMMAR` (estructura esperada de cada nodo)

Describe qué hijos puede tener cada tipo de nodo. Útil para validación.

```python
GRAMMAR = {
    "document": {"children": ["heading", "paragraph", "list", "code_block", "hr"]},
    "heading": {"children": ["text"], "meta": ["level"]},
    "paragraph": {"children": ["text"]},
    "list": {"children": ["list_item"]},
    "list_item": {"children": ["text"]},
    "code_block": {"children": [], "meta": ["lang", "content"]},
    "hr": {"children": []},
    "text": {"children": []},
}
```

### Contenido Opcional Útil

- **Inline tokens**: para fase de inline pass (énfasis, código inline, enlaces).
- **Políticas configurables**:
  ```python
  LIST_INDENT = 2
  MAX_HEADING_LEVEL = 6
  ALLOW_HTML = False
  ```
- **Perfiles** (ej. "GFM", "CommonMark", "strict"): diccionarios que activan/desactivan features.

### Pseudocódigo de Compilación de Specs

```text
función compile_master_regex(BLOCK_ORDER, TOKENS):
    patrones ← []
    para cada tipo en BLOCK_ORDER:
        regex ← TOKENS[tipo]
        patrones.append( f"(?P<{tipo}>{regex})" )
    retornar re.compile("|".join(patrones), re.MULTILINE)
```

**No duplicar orden**: `BLOCK_ORDER` es la única lista que define prioridades. No crear un dict `PRIORITIES = {"HEADING":1, ...}` aparte.

### Pitfalls y Buenas Prácticas

| ❌ Evitar | ✅ Hacer |
|-----------|----------|
| Diccionarios `{"HEADING":"HEADING"}` sin propósito | Usar claves directamente o constantes |
| Prioridades numéricas en dict separado | Lista `BLOCK_ORDER` única |
| Regex sin grupos nombrados | Siempre `(?P<nombre>...)` |
| Catch-all (`TEXT`) al principio | Siempre al final |
| Lógica de creación de nodos aquí | Delegar a `parser.make_node()` |

## [4].lexer

### Descripción Breve

Convierte texto crudo en una **lista de tokens**. Cada token es un dict con `{type, line, meta}`. El lexer **no interpreta** relaciones entre tokens (eso es trabajo del parser).

### Estructura de un Token

```python
{
    "type": "HEADING_ATX",
    "line": 3,
    "meta": {"level": 2, "content": "Introducción"}
}
```

- **type**: string, debe estar en `BLOCK_ORDER`.
- **line**: número de línea (1-based).
- **meta**: dict con datos capturados por grupos nombrados del regex.

### Entrada/Salida

| Entrada | Salida |
|---------|--------|
| `"# Hola\n\nTexto."` | `[{type:"HEADING_ATX", line:1, meta:{level:1, content:"Hola"}}, {type:"BLANK_LINE", line:2, meta:{}}, {type:"TEXT", line:3, meta:{content:"Texto."}}]` |

### Orden de Prueba

El lexer itera línea por línea. Para cada línea, prueba regex **en el orden de `BLOCK_ORDER`**. Primera coincidencia gana.

```text
función tokenize(text):
    tokens ← []
    líneas ← text.split("\n")
    para cada (línea, número) en líneas:
        para cada tipo en BLOCK_ORDER:
            si TOKENS[tipo].match(línea):
                meta ← extraer_grupos_nombrados(match)
                tokens.append({type: tipo, line: número, meta: meta})
                romper  # primera coincidencia gana
    retornar tokens
```

### Emisión de `BLANK_LINE`

**Importante**: las líneas en blanco **deben emitir token `BLANK_LINE`**. El parser las usa para separar párrafos.

```python
# Mal: ignorar líneas en blanco
if not line.strip():
    continue  # ❌

# Bien: emitir token
if not line.strip():
    tokens.append({"type": "BLANK_LINE", "line": num, "meta": {}})
```

### Mini-Ejemplo Real

Entrada:
```markdown
# Hola
Este es un párrafo.
```

Tokens generados:
```python
[
    {"type": "HEADING_ATX", "line": 1, "meta": {"level": 1, "content": "Hola"}},
    {"type": "TEXT", "line": 2, "meta": {"content": "Este es un párrafo."}}
]
```

### Pitfalls y Buenas Prácticas

| ❌ Evitar | ✅ Hacer |
|-----------|----------|
| Ignorar `BLANK_LINE` | Emitir token explícito |
| Crear nodos AST aquí | Solo tokens; AST es del parser |
| Hardcodear orden de regex | Respetar `BLOCK_ORDER` de specs |
| Tokens sin `line` | Siempre incluir posición |

## [5].parser

### Descripción Breve

Convierte la **lista de tokens** en un **árbol de nodos** (AST). Maneja lógica de agrupación: párrafos multi-línea, series de elementos (listas), estados (code fences abiertos).

### Entrada/Salida

| Entrada | Salida |
|---------|--------|
| `[{type:"TEXT",...}, {type:"TEXT",...}, {type:"BLANK_LINE",...}]` | `{type:"document", children:[{type:"paragraph", children:[...]}]}` |

### Conceptos Clave

#### 5.1. Diferencia entre Token y Nodo

- **Token**: representa una línea cruda identificada (`HEADING_ATX`, `TEXT`).
- **Nodo**: representa una construcción semántica del AST (`heading`, `paragraph`).

Un `TEXT` token puede convertirse en nodo `paragraph` (si hay varios `TEXT` consecutivos) o en `text` (hoja del AST).

#### 5.2. Buffers y Estados

- **Buffer de párrafo**: acumula tokens `TEXT` consecutivos hasta encontrar `BLANK_LINE` o token no-text.
- **Estado de code fence**: bandera que indica si estamos dentro de ` ``` ... ``` `.

```text
función parse(tokens):
    ast ← {type: "document", children: []}
    buffer_párrafo ← []
    dentro_fence ← False
    
    para cada token en tokens:
        si dentro_fence:
            si token.type == "CODE_FENCE_END":
                flush_code_block()
                dentro_fence ← False
            sino:
                acumular_línea_código()
        sino:
            si token.type == "CODE_FENCE_START":
                flush_paragraph(buffer_párrafo)
                dentro_fence ← True
            sino si token.type == "TEXT":
                buffer_párrafo.append(token)
            sino si token.type == "BLANK_LINE":
                flush_paragraph(buffer_párrafo)
            sino:
                flush_paragraph(buffer_párrafo)
                nodo ← make_node(token)
                ast.children.append(nodo)
    
    flush_paragraph(buffer_párrafo)  # flush final
    retornar ast
```

#### 5.3. `make_node` (Pseudocódigo)

```text
función make_node(token):
    tipo_nodo ← mapear_token_a_nodo(token.type)
    nodo ← {type: tipo_nodo, children: []}
    
    si tipo_nodo == "heading":
        nodo["level"] = token.meta["level"]
        nodo.children.append({type: "text", value: token.meta["content"]})
    
    si tipo_nodo == "hr":
        # sin children
    
    retornar nodo
```

#### 5.4. `flush_paragraph` (Pseudocódigo)

```text
función flush_paragraph(buffer):
    si buffer está vacío:
        retornar
    
    contenido ← unir(buffer, separador=" ")
    nodo_texto ← {type: "text", value: contenido}
    nodo_párrafo ← {type: "paragraph", children: [nodo_texto]}
    ast.children.append(nodo_párrafo)
    
    vaciar(buffer)
```

### Relación con `GRAMMAR`

El parser **no valida** que los nodos cumplan gramática (eso es del validator). Solo construye el árbol según lógica de agrupación. Ejemplo:

- Token `HEADING_ATX` → nodo `heading` con hijo `text`.
- Serie de tokens `TEXT` → nodo `paragraph` con hijos `text`.

Pero no verifica si `heading` puede estar dentro de `list` (validación posterior).

### Pitfalls y Buenas Prácticas

| ❌ Evitar | ✅ Hacer |
|-----------|----------|
| No hacer flush final | Siempre `flush_paragraph` al terminar |
| Mezclar validación aquí | Parser solo construye; validator valida |
| Ignorar `BLANK_LINE` | Usarlo como señal de fin de bloque |
| Estados globales mutables | Pasar estados como parámetros o contexto explícito |

## [6].validator

### Descripción Breve

Recorre el AST y aplica **reglas declarativas** que dependen del contexto (tipo de nodo padre, profundidad, etc.). Genera lista de errores/warnings **sin modificar el AST**.

### Validación Temprana vs Posterior

| Fase | Qué valida | Ejemplo |
|------|------------|---------|
| **Lexer** | Sintaxis básica de línea | "Heading debe empezar con `#`" |
| **Parser** | Agrupación mínima | "Code fence sin cierre" (opcional aquí) |
| **Validator** | Reglas contextuales profundas | "No encabezados dentro de listas", "Max 6 niveles de heading" |

**Criterio**: valida en lexer/parser solo si es **imprescindible para continuar** (ej. regex no match). Todo lo demás va en validator para mantener parser simple.

### Reglas Declarativas MDxx

Estilo de validación inspirado en linters Markdown (ej. markdownlint). Cada regla tiene código y descripción.

```python
VALIDATION_RULES = {
    "MD001": {
        "name": "heading-increment",
        "description": "Los niveles de heading deben incrementar de uno en uno",
        "check": lambda node, context: validate_heading_increment(node, context)
    },
    "MD003": {
        "name": "heading-style",
        "description": "Todos los headings deben ser ATX (no Setext)",
        "check": lambda node, context: validate_heading_style(node, context)
    },
    "MD022": {
        "name": "blanks-around-headings",
        "description": "Headings deben tener blank line antes/después",
        "check": lambda node, context: validate_blanks_around(node, context)
    },
}
```

### Pseudocódigo de Validación

```text
función validate(ast):
    errores ← []
    contexto ← {nivel_heading_previo: 0, parent: None}
    
    recorrer_ast(ast, contexto, función(nodo, ctx):
        para cada regla en VALIDATION_RULES:
            resultado ← regla.check(nodo, ctx)
            si no resultado.ok:
                errores.append({
                    code: regla.code,
                    message: regla.description,
                    line: nodo.line
                })
    )
    
    retornar {ast: ast, errores: errores}
```

### Diferencia Errores Duros vs Estilo

- **Errores duros** (parse): impiden construir AST (ej. regex no match, fence sin cerrar).
- **Errores de estilo** (validator): AST válido pero no cumple políticas (ej. heading sin blank line).

**Decisión de diseño**: el validator puede emitir **warnings** (no bloquean) o **errores** (bloquean renderizado). Configurable por regla.

### Mini-Ejemplo

AST:
```python
{
    "type": "document",
    "children": [
        {"type": "heading", "level": 1, "children": [...]},
        {"type": "heading", "level": 3, "children": [...]},  # ❌ MD001
    ]
}
```

Error emitido:
```python
{
    "code": "MD001",
    "message": "Heading incrementa de 1 a 3 (debería ser 2)",
    "line": 5,
    "severity": "warning"
}
```

### Pitfalls y Buenas Prácticas

| ❌ Evitar | ✅ Hacer |
|-----------|----------|
| Validar en parser cosas no críticas | Delegar a validator |
| Modificar AST en validación | Solo lectura, emitir errores |
| Hardcodear reglas | Tabla declarativa de reglas |
| No capturar contexto (parent, siblings) | Pasar contexto explícito |

## [7].renderer

### Descripción Breve

Convierte el AST en **HTML seguro**. Mapea cada tipo de nodo a etiquetas HTML, aplica escape de caracteres especiales y genera atributos mínimos.

### Tabla Nodo → Etiqueta HTML

| Tipo de Nodo | Etiqueta HTML | Atributos |
|--------------|---------------|-----------|
| `document` | `<div>` (o sin etiqueta) | `class="markdown-body"` |
| `heading` | `<h1>` a `<h6>` | Según `level` |
| `paragraph` | `<p>` | — |
| `list` | `<ul>` o `<ol>` | Según `ordered` |
| `list_item` | `<li>` | — |
| `code_block` | `<pre><code>` | `class="language-{lang}"` |
| `hr` | `<hr>` | — |
| `text` | Texto plano | Escape obligatorio |

### Escape Seguro

**Obligatorio**: usar `html.escape()` para contenido textual.

```python
import html

def render_text(node):
    return html.escape(node["value"])
```

**No hacer**: renderizar texto crudo sin escape (vulnerabilidad XSS).

### Pseudocódigo

```text
función to_html(nodo):
    si nodo.type == "text":
        retornar html.escape(nodo.value)
    
    si nodo.type == "heading":
        nivel ← nodo.level
        contenido ← to_html(nodo.children[0])
        retornar f"<h{nivel}>{contenido}</h{nivel}>"
    
    si nodo.type == "paragraph":
        hijos ← [to_html(hijo) para hijo en nodo.children]
        retornar f"<p>{unir(hijos)}</p>"
    
    si nodo.type == "code_block":
        lang ← nodo.meta.get("lang", "")
        código ← html.escape(nodo.meta["content"])
        retornar f'<pre><code class="language-{lang}">{código}</code></pre>'
    
    si nodo.type == "hr":
        retornar "<hr>"
    
    si nodo.type == "document":
        hijos ← [to_html(hijo) para hijo en nodo.children]
        retornar unir(hijos, "\n")
```

### Atributos Mínimos

- Code blocks: `class="language-{lang}"` para syntax highlighting (ej. Prism.js, highlight.js).
- Document: `class="markdown-body"` para estilos CSS consistentes (ej. github-markdown-css).

### Mini-Ejemplo

AST:
```python
{
    "type": "heading",
    "level": 2,
    "children": [{"type": "text", "value": "Intro & <script>"}]
}
```

HTML generado:
```html
<h2>Intro &amp; &lt;script&gt;</h2>
```

### Pitfalls y Buenas Prácticas

| ❌ Evitar | ✅ Hacer |
|-----------|----------|
| No escapar HTML | Siempre `html.escape()` |
| Hardcodear etiquetas en múltiples lugares | Tabla de mapeo centralizada |
| Inyectar atributos sin sanitizar | Whitelist de atributos permitidos |
| Renderizar inline pass aquí | Separar en módulo `inline.py` |

## [8].crecimiento_incremental

### MVP (Fase 0)

**Objetivo**: validar pipeline completo con mínimo subset.

- Tokens: `HEADING_ATX`, `TEXT`, `BLANK_LINE`
- Nodos: `document`, `heading`, `paragraph`, `text`
- Testing: 3 archivos `.md` en `tests/fixtures/`

**Criterio de éxito**: `main.py` convierte heading + párrafo → HTML válido.

### Fase 1: Bloques Adicionales

Agregar:

- `HR` (regla horizontal)
- `CODE_FENCE` (bloques de código)
- `LIST_ITEM` (listas simples sin nesting)

**Cambios**:

- `specs`: 3 nuevos tokens en `BLOCK_ORDER`
- `parser`: estados para fence, buffer para listas
- `renderer`: mapeo de `hr`, `code_block`, `list`

### Fase 2: Inline Pass

Procesar contenido de nodos `text` para detectar:

- Énfasis: `*cursiva*`, `**negrita**`
- Código inline: `` `código` ``
- Enlaces: `[texto](url)`
- Imágenes: `![alt](url)`

**Implementación**:

1. Crear `inline.py` con función `parse_inline(text) → list[nodos]`
2. Modificar `renderer.render_text()` para llamar `parse_inline()`
3. Agregar `INLINE_TOKENS` a `specs`

### Fase 3: Listas Anidadas

**Desafío**: detectar indentación y construir árboles de listas.

**Solución**:

- Agregar `indent` a meta de `LIST_ITEM` tokens
- En parser, mantener stack de profundidades
- Validador verifica niveles consistentes

### Fase 4: Setext Headings

```markdown
Heading
=======
```

**Cambios**:

- Lexer: detectar línea con `===` o `---` después de `TEXT`
- Parser: convertir `TEXT` previo en `heading` retroactivamente

### Fase 5: Tablas (GFM)

```markdown
| Col1 | Col2 |
|------|------|
| A    | B    |
```

**Desafío**: tokens multi-línea, detección de alineación.

### Fase 6: Perfiles Configurables

```python
PROFILES = {
    "strict": {
        "allow_html": False,
        "max_heading_level": 6,
        "require_blank_around_headings": True
    },
    "gfm": {
        "tables": True,
        "task_lists": True,
        "strikethrough": True
    }
}
```

Cargar perfil al inicio: `specs.load_profile("gfm")`.

### Ambigüedades entre Módulos

**Clarificación**:

- Lexer NO decide si un `TEXT` es parte de un párrafo → eso es del parser.
- Parser NO valida si un heading puede estar dentro de una lista → eso es del validator.
- Validator NO modifica AST → solo emite errores.
- Renderer NO valida → asume AST válido.

Cada módulo tiene **una responsabilidad única**.

### Referencias a Criterios Adoptados

#### Orden de Tokens (BLOCK_ORDER)

**Criterio**: Siguiendo convenciones de parsers descendentes (top-down), patrones más específicos primero para evitar ambigüedades. Similar a orden en especificación CommonMark (aunque simplificado).

#### Escape de HTML

**Criterio**: `html.escape()` es el estándar de Python para prevenir XSS. Alternativas (bleach, MarkupSafe) agregan dependencias innecesarias para MVP.

#### Validación Declarativa

**Criterio**: Inspirado en markdownlint (códigos MDxxx) para familiaridad con usuarios que usan linters Markdown.

#### AST sin POO

**Criterio**: Dicts/lists son suficientes para estructuras arbóreas simples. Evita overhead de clases y permite serialización directa (JSON). Inspirado en AST de Babel (JavaScript).

### Correcciones Aplicadas

1. **Eliminada redundancia**: No se proponen diccionarios `{"HEADING":"HEADING"}`.
2. **Orden único**: `BLOCK_ORDER` es la única fuente de verdad.
3. **Límites claros**: Cada módulo tiene responsabilidad única y explícita.
4. **Catch-all al final**: `TEXT` siempre es último en `BLOCK_ORDER`.
5. **Validación separada**: Parser construye, validator valida (no mezclado).
