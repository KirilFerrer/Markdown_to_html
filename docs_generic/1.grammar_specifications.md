# Grammar Specifications: Defining Language Syntax

## [1].motivation_for_formal_grammar

### Why Start with Grammar Definition?

A **formal grammar** is the foundation of any language processing pipeline. Before writing a single line of lexer or parser code, you must define:

- What syntactic constructs are valid in your language?
- In what order should ambiguous patterns be evaluated?
- What information should be captured from each construct?
- How do AST nodes relate to each other?

### Benefits of Formal Grammar

#### 1. Design Validation Without Implementation

You can review token patterns, precedence rules, and node structures without implementing the entire pipeline.

**Example**: Catch ambiguous patterns early:
```text
❌ Ambiguous:
  KEYWORD = /^\w+/
  IDENTIFIER = /^\w+/
  # Both match "function" - which wins?

✅ Clear:
  KEYWORD = /^(function|return|if)\b/
  IDENTIFIER = /^[a-zA-Z_]\w*/
  # Keywords checked first, identifiers second
```

#### 2. Single Source of Truth

All phases (lexer, parser, validator, generator) reference the same grammar. Changes propagate automatically.

**Antipattern: Distributed Grammar**:
```text
❌ lexer.py:     MAX_DEPTH = 10
❌ parser.py:    MAX_NESTING = 10
❌ validator.py: DEPTH_LIMIT = 10
# Three places define the same rule!
```

**Solution: Centralized Grammar**:
```text
✅ grammar.py: MAX_NESTING_DEPTH = 10
✅ lexer imports grammar.MAX_NESTING_DEPTH
✅ parser imports grammar.MAX_NESTING_DEPTH
✅ validator imports grammar.MAX_NESTING_DEPTH
```

#### 3. Facilitates Testing

You can test token patterns independently before integration.

```text
import grammar

pattern = compile_pattern(grammar.TOKENS["NUMBER"])
assert pattern.match("42")
assert not pattern.match("abc")
```

#### 4. Living Documentation

Grammar serves as machine-readable specification of the language.

**Use cases**:
- Generate syntax highlighting rules
- Build IDE autocomplete
- Create language documentation
- Validate test fixtures

## [2].components_of_grammar

### Overview

A complete grammar specification consists of four main components:

```text
┌─────────────────────────────────────┐
│          GRAMMAR SPECIFICATION      │
├─────────────────────────────────────┤
│  1. Token Definitions (Lexical)    │  ← Patterns for atomic elements
│  2. Precedence Rules (Priority)    │  ← Disambiguation strategy
│  3. Node Types (AST Vocabulary)    │  ← Categories of syntax tree nodes
│  4. Structural Rules (Syntax)      │  ← Parent-child relationships
└─────────────────────────────────────┘
```

### Component 1: Token Definitions

**Purpose**: Define patterns that identify atomic lexical elements.

**Structure**:
```text
TOKEN_TYPE = {
    "name": string,
    "pattern": regex_string,
    "captures": [named_group_1, named_group_2, ...]
}
```

**Example: Arithmetic Expression Grammar**
```text
TOKENS = {
    "NUMBER": {
        "pattern": r"^\d+(\.\d+)?",
        "captures": ["value"]
    },
    "OPERATOR_PLUS": {
        "pattern": r"^\+",
        "captures": []
    },
    "OPERATOR_MULT": {
        "pattern": r"^\*",
        "captures": []
    },
    "PAREN_OPEN": {
        "pattern": r"^\(",
        "captures": []
    },
    "PAREN_CLOSE": {
        "pattern": r"^\)",
        "captures": []
    },
    "IDENTIFIER": {
        "pattern": r"^[a-zA-Z_]\w*",
        "captures": ["name"]
    }
}
```

**Key Principle**: Use **named capture groups** for metadata extraction:
```text
r"^(?P<value>\d+)"     → Extracts number value
r"^(?P<name>[a-zA-Z]+)" → Extracts identifier name
```

### Component 2: Precedence Rules

**Purpose**: Resolve ambiguity when multiple patterns could match the same input.

**Implementation**: Ordered list of token types (most specific first).

```text
TOKEN_PRECEDENCE = [
    "KEYWORD_FUNCTION",  # Specific: matches only "function"
    "KEYWORD_RETURN",    # Specific: matches only "return"
    "IDENTIFIER",        # General: matches any word
    "WHITESPACE"         # Catch-all: matches spaces
]
```

**Principle**: **Specific before General, Catch-all Last**.

**Example of Precedence Failure**:
```text
Input: "function add(x, y) { return x + y; }"

❌ Wrong precedence:
  TOKEN_PRECEDENCE = ["IDENTIFIER", "KEYWORD_FUNCTION"]
  Result: "function" matched as IDENTIFIER (not KEYWORD_FUNCTION)

✅ Correct precedence:
  TOKEN_PRECEDENCE = ["KEYWORD_FUNCTION", "IDENTIFIER"]
  Result: "function" matched as KEYWORD_FUNCTION ✓
```

### Component 3: Node Types

**Purpose**: Define vocabulary of AST node categories.

**Structure**: Set or list of valid node type strings.

```text
NODE_TYPES = {
    # Root
    "program",
    
    # Statements
    "function_declaration",
    "if_statement",
    "return_statement",
    "assignment",
    
    # Expressions
    "binary_expression",
    "unary_expression",
    "call_expression",
    
    # Literals
    "identifier",
    "number_literal",
    "string_literal"
}
```

**Design Consideration**: How many node types?

| Approach | Pros | Cons |
|----------|------|------|
| **Coarse-grained** (few types) | Simple, less code | Less semantic info in AST |
| **Fine-grained** (many types) | Precise, rich semantics | Complex, harder to maintain |

**Recommendation**: Start coarse, refine as needed.

### Component 4: Structural Rules (Grammar)

**Purpose**: Define valid parent-child relationships and required/optional attributes.

**Format**: Dictionary mapping node types to structural constraints.

```text
GRAMMAR = {
    "program": {
        "children": ["function_declaration", "if_statement", "assignment"],
        "attributes": [],
        "required": [],
        "optional": []
    },
    "function_declaration": {
        "children": ["identifier", "parameter_list", "block"],
        "attributes": ["name"],
        "required": ["name", "parameters", "body"],
        "optional": []
    },
    "binary_expression": {
        "children": ["expression", "expression"],  # Left and right operands
        "attributes": ["operator"],
        "required": ["left", "right", "operator"],
        "optional": []
    },
    "identifier": {
        "children": [],  # Leaf node
        "attributes": ["name"],
        "required": ["name"],
        "optional": []
    }
}
```

**Usage**: Validator checks AST nodes against these rules.

**Example Validation**:
```text
AST node: {type: "binary_expression", left: {...}, operator: "+"}

Check GRAMMAR["binary_expression"]:
  ✓ Has attribute "operator"
  ❌ Missing attribute "right"
  
Error: "binary_expression requires 'right' operand"
```

## [3].bnf_and_ebnf_notation

### Backus-Naur Form (BNF)

**BNF** is a formal notation for describing context-free grammars.

**Syntax**:
```text
<non-terminal> ::= production_rule | alternative_rule
```

**Example: Simple Arithmetic**
```bnf
<expression> ::= <term> | <expression> "+" <term>
<term>       ::= <factor> | <term> "*" <factor>
<factor>     ::= <number> | "(" <expression> ")"
<number>     ::= "0" | "1" | "2" | ... | "9"
```

**Interpretation**:
- `<expression>` is either a single `<term>` OR `<expression> + <term>`
- `<term>` is either a single `<factor>` OR `<term> * <factor>`
- Recursion enables arbitrary nesting (e.g., `1 + 2 * (3 + 4)`)

### Extended BNF (EBNF)

**EBNF** adds convenience operators for common patterns.

| Operator | Meaning | Example |
|----------|---------|---------|
| `*` | Zero or more | `<digit>*` → "", "1", "123" |
| `+` | One or more | `<digit>+` → "1", "123" (not "") |
| `?` | Optional (zero or one) | `<sign>?` → "", "+", "-" |
| `|` | Alternation | `"+" | "-"` → "+" OR "-" |
| `()` | Grouping | `("+" | "-")?` → optional sign |

**Example: Function Definition (EBNF)**
```ebnf
function_def = "function" identifier "(" parameter_list? ")" block
parameter_list = identifier ("," identifier)*
block = "{" statement* "}"
statement = assignment | if_statement | return_statement
```

**Translation to Implementation**:
```text
EBNF: parameter_list = identifier ("," identifier)*

Pseudocode:
  function parse_parameter_list():
      params = [parse_identifier()]
      while match(","):
          consume(",")
          params.append(parse_identifier())
      return params
```

### BNF vs Implementation Grammar

**BNF/EBNF**: Theoretical, for specification.

**Implementation Grammar** (this document's format): Practical, maps to data structures.

**Conversion**:
```text
BNF:
  <expression> ::= <term> | <expression> "+" <term>

Implementation Grammar:
  GRAMMAR = {
      "expression": {
          "children": ["term", "binary_expression"],
          "attributes": []
      },
      "binary_expression": {
          "children": ["expression", "expression"],
          "attributes": ["operator"]
      }
  }
```

## [4].architectural_decisions

### Decision 1: String Literals vs Enums for Token Types

#### Option A: String Literals (✅ Simple for MVP)

```text
TOKEN_TYPES = ["KEYWORD", "IDENTIFIER", "NUMBER"]

if token.type == "KEYWORD":
    # ...
```

**Pros**: Minimal boilerplate, JSON-serializable.

**Cons**: No IDE autocomplete, typos undetected.

#### Option B: Enums (✅ Recommended for Large Projects)

```text
from enum import Enum

class TokenType(str, Enum):
    KEYWORD = "KEYWORD"
    IDENTIFIER = "IDENTIFIER"
    NUMBER = "NUMBER"

if token.type == TokenType.KEYWORD:
    # ...
```

**Pros**: Type safety, autocomplete, refactoring-friendly.

**Cons**: More verbose.

**Recommendation**: Start with strings, migrate to enums when project grows beyond 20 token types.

### Decision 2: Precedence as List vs Dictionary

#### Option A: Dictionary with Numeric Priorities (❌ Redundant)

```text
PRECEDENCE = {
    "KEYWORD": 1,
    "IDENTIFIER": 2,
    "WHITESPACE": 99
}

# Must sort: sorted(PRECEDENCE, key=PRECEDENCE.get)
```

**Problem**: Priority is implicit in order. Dictionary adds no value.

#### Option B: Ordered List (✅ Recommended)

```text
TOKEN_PRECEDENCE = [
    "KEYWORD",     # Implicit priority 0 (highest)
    "IDENTIFIER",  # Implicit priority 1
    "WHITESPACE"   # Implicit priority 2 (lowest)
]
```

**Advantage**: Order IS priority. Reordering is visual (move lines).

### Decision 3: Regex Compilation Strategy

#### Option A: Compile on Every Match (❌ Inefficient)

```text
import re

for line in source_lines:
    if re.match(r"^function\b", line):  # Compiles every iteration
        # ...
```

**Problem**: Regex compilation is expensive (O(pattern_complexity)). Repeating N times wastes cycles.

#### Option B: Pre-compile Individual Patterns (⚠️ Verbose)

```text
KEYWORD_PATTERN = re.compile(r"^function\b")
IDENTIFIER_PATTERN = re.compile(r"^[a-zA-Z_]\w*")

if KEYWORD_PATTERN.match(line):
    # ...
elif IDENTIFIER_PATTERN.match(line):
    # ...
```

**Pros**: Efficient, explicit.

**Cons**: Boilerplate for each pattern.

#### Option C: Master Regex with Named Groups (✅ Optimal)

```text
MASTER_PATTERN = re.compile(
    r"(?P<KEYWORD>^function\b)|(?P<IDENTIFIER>^[a-zA-Z_]\w*)",
    re.MULTILINE
)

match = MASTER_PATTERN.match(line)
if match:
    token_type = match.lastgroup  # "KEYWORD" or "IDENTIFIER"
```

**Pros**: Single compilation, automatic type identification.

**Cons**: Complex regex harder to debug.

**Recommendation**: Use master regex for production, individual patterns for prototyping.

### Decision 4: Named Groups vs Positional Capture

#### Option A: Positional Capture (❌ Fragile)

```text
pattern = r"^(\w+)\s*=\s*(\d+)"
match = pattern.match("x = 42")

name = match.group(1)   # First group
value = match.group(2)  # Second group
```

**Problem**: Adding a group shifts indices. Regex `^(const\s+)?(\w+)\s*=\s*(\d+)` breaks code.

#### Option B: Named Capture (✅ Robust)

```text
pattern = r"^(?P<name>\w+)\s*=\s*(?P<value>\d+)"
match = pattern.match("x = 42")

name = match.group("name")
value = match.group("value")
```

**Advantage**: Semantic labels. Refactoring regex doesn't break extraction code.

**Recommendation**: **Always use named groups** for any data you need to extract.

## [5].precedence_and_ambiguity

### Sources of Ambiguity

#### 1. Overlapping Patterns

```text
KEYWORD = r"^\w+"
IDENTIFIER = r"^\w+"
```

**Problem**: Both match "function". Without precedence, result is undefined.

**Solution**: Keywords before identifiers in precedence list.

#### 2. Prefix Matching

```text
OPERATOR_GE = r"^>="
OPERATOR_GT = r"^>"
```

**Problem**: ">=" matches both (">=" starts with ">").

**Solution**: Longer pattern first.

```text
TOKEN_PRECEDENCE = ["OPERATOR_GE", "OPERATOR_GT"]
```

#### 3. Catch-All at Wrong Position

```text
TEXT = r"^.+"  # Matches any non-empty line
```

**Problem**: If `TEXT` is first, nothing else ever matches.

**Solution**: Catch-all patterns **must be last**.

```text
TOKEN_PRECEDENCE = [
    "KEYWORD",
    "IDENTIFIER",
    "NUMBER",
    "TEXT"  # ← Last resort
]
```

### Resolving Ambiguity

#### Strategy 1: Longest Match Wins

When multiple patterns match, choose the one consuming the most characters.

```text
Input: ">="

Matches:
  OPERATOR_GT (">"):   length 1
  OPERATOR_GE (">="): length 2

Choose: OPERATOR_GE (longest)
```

**Implementation**: Sort patterns by max match length (descending), or use alternation with longest first.

#### Strategy 2: First Match Wins

Evaluate patterns in precedence order. First to match wins.

```text
Input: "function"

Precedence: [KEYWORD_FUNCTION, IDENTIFIER]

1. Try KEYWORD_FUNCTION (/^function\b/) → Match ✓
2. Don't try IDENTIFIER (already matched)

Result: KEYWORD_FUNCTION
```

**Implementation**: Iterate through precedence list, return first match.

#### Strategy 3: Contextual Disambiguation

Use lexer state to resolve ambiguity.

```text
Input: "/"

Context: Inside string → "/" is TEXT
Context: Normal → "/" is OPERATOR_DIV
Context: After another "/" → Start of comment
```

**Implementation**: Maintain `state` variable, check before matching.

### Precedence Rules for Common Patterns

| Pattern Type | Precedence (High → Low) | Rationale |
|--------------|------------------------|-----------|
| **Multi-char operators** | Before single-char | ">=" before ">" |
| **Keywords** | Before identifiers | "if" before generic word |
| **Numbers with decimals** | Before integers | "3.14" before "3" |
| **Specific constructs** | Before generic | Code fence "```" before text |
| **Catch-all** | Last | TEXT matches anything |

## [6].grammar_for_specific_languages

### Case 1: Python (Indentation-Sensitive)

**Challenge**: Whitespace is syntactically significant.

**Grammar Additions**:
```text
TOKENS = {
    "INDENT": {
        "pattern": r"^(    )+",  # 4 spaces per level
        "captures": ["level"]
    },
    "DEDENT": {
        "pattern": None,  # Virtual token, emitted by lexer
        "captures": []
    },
    "NEWLINE": {
        "pattern": r"^\n",
        "captures": []
    }
}
```

**Lexer State**: Track `indent_stack` to emit INDENT/DEDENT tokens.

### Case 2: SQL (Case-Insensitive Keywords)

**Challenge**: `SELECT`, `Select`, `select` are equivalent.

**Grammar Solution**:
```text
TOKENS = {
    "KEYWORD_SELECT": {
        "pattern": r"^(?i:select)\b",  # (?i:...) = case-insensitive
        "captures": []
    }
}
```

**Alternative**: Normalize input to uppercase before lexing.

### Case 3: JavaScript (Automatic Semicolon Insertion)

**Challenge**: Semicolons are optional in some contexts.

**Grammar Rule**: Parser must track newlines and insert virtual semicolons.

```text
GRAMMAR = {
    "statement": {
        "terminator": "SEMICOLON | NEWLINE | EOF"
    }
}
```

**Parser Logic**:
```text
if next_token == NEWLINE and current_statement_complete():
    insert_virtual_semicolon()
```

### Case 4: C (Preprocessor Directives)

**Challenge**: `#include`, `#define` are lexically distinct from normal code.

**Grammar Strategy**: Separate token type for directives.

```text
TOKENS = {
    "DIRECTIVE": {
        "pattern": r"^#\s*\w+",
        "captures": ["directive_name"]
    }
}

TOKEN_PRECEDENCE = ["DIRECTIVE", "KEYWORD", ...]  # Directives first
```

### Case 5: Markdown (Context-Dependent Syntax)

**Challenge**: `*` can be list marker, emphasis, or HR depending on context.

**Grammar Solution**: Use lexer state.

```text
State: START_OF_LINE
  "*" → LIST_MARKER (if followed by space)
  "***" → HR (if entire line)

State: INLINE
  "*text*" → EMPHASIS
```

### Case 6: JSON (Fixed Structure)

**Challenge**: JSON has very simple, fixed grammar.

**Grammar (Minimal)**:
```text
TOKENS = {
    "LBRACE": {"pattern": r"^\{"},
    "RBRACE": {"pattern": r"^\}"},
    "LBRACKET": {"pattern": r"^\["},
    "RBRACKET": {"pattern": r"^\]"},
    "COLON": {"pattern": r"^:"},
    "COMMA": {"pattern": r"^,"},
    "STRING": {"pattern": r'^"([^"\\]|\\.)*"'},
    "NUMBER": {"pattern": r"^-?\d+(\.\d+)?([eE][+-]?\d+)?"},
    "BOOLEAN": {"pattern": r"^(true|false)"},
    "NULL": {"pattern": r"^null"}
}

GRAMMAR = {
    "object": {"children": ["member*"]},
    "array": {"children": ["value*"]},
    "value": {"children": ["object | array | STRING | NUMBER | BOOLEAN | NULL"]}
}
```

**Advantage**: Simple grammar enables fast parsing.

## [8].common_pitfalls

### Pitfall 1: Duplicated Grammar Rules

❌ **Bad**: Same rule defined in multiple places

```text
# lexer.py
MAX_IDENTIFIER_LENGTH = 64

# parser.py
IDENTIFIER_LIMIT = 64

# validator.py
def check_identifier(name):
    if len(name) > 64:  # Hardcoded!
```

✅ **Good**: Single source of truth

```text
# grammar.py
MAX_IDENTIFIER_LENGTH = 64

# All modules import from grammar.py
```

### Pitfall 2: Order-Dependent Bugs

❌ **Bad**: Catch-all before specific

```text
TOKEN_PRECEDENCE = [
    "TEXT",         # ❌ Matches everything
    "KEYWORD",      # Never reached
]
```

✅ **Good**: Specific before general

```text
TOKEN_PRECEDENCE = [
    "KEYWORD",
    "IDENTIFIER",
    "TEXT"          # Last resort
]
```

### Pitfall 3: Regex Without Anchors

❌ **Bad**: Pattern matches anywhere

```text
"NUMBER": r"\d+"  # Matches "3" in "abc3def"
```

✅ **Good**: Anchored pattern

```text
"NUMBER": r"^\d+"  # Matches only at start
```

### Pitfall 4: Ambiguous Keywords

❌ **Bad**: Keyword pattern too broad

```text
"KEYWORD": r"^(if|in|int)"  # "in" matches start of "int"
```

✅ **Good**: Word boundaries

```text
"KEYWORD": r"^(if|in|int)\b"  # \b ensures word boundary
```

### Pitfall 5: Grammar in Lexer

❌ **Bad**: Lexer contains structural rules

```text
# lexer.py
if token.type == "IDENTIFIER" and previous_token.type == "KEYWORD_FUNCTION":
    token.role = "function_name"
```

✅ **Good**: Lexer emits tokens, parser builds structure

```text
# lexer.py
return {"type": "IDENTIFIER", "value": token_text}

# parser.py
if previous_token.type == "KEYWORD_FUNCTION":
    node = {"type": "function_declaration", "name": current_token}
```

## [9].optimization_techniques

### Technique 1: Regex Compilation

**Problem**: Compiling regex on every match is slow.

**Solution**: Compile once at import time.

```text
# Module-level compilation
COMPILED_TOKENS = {
    token_type: re.compile(pattern)
    for token_type, pattern in TOKENS.items()
}
```

**Speedup**: 10-100x for complex patterns.

### Technique 2: Trie-Based Keyword Matching

**Problem**: Long list of keywords requires many regex evaluations.

**Solution**: Build a trie (prefix tree).

```text
KEYWORDS = {"if", "else", "function", "return"}

# Build trie
keyword_trie = build_trie(KEYWORDS)

# Match in O(k) where k = keyword length
if lookup_trie(keyword_trie, input_string):
    return "KEYWORD"
```

**Speedup**: O(k) vs O(n) where n = number of keywords.

### Technique 3: Memoization for Repeated Patterns

**Problem**: Same subpattern tested multiple times.

**Solution**: Cache match results.

```text
match_cache = {}

def cached_match(pattern, text):
    key = (pattern, text)
    if key not in match_cache:
        match_cache[key] = pattern.match(text)
    return match_cache[key]
```

**Speedup**: Significant for backtracking parsers.

### Technique 4: Lazy Compilation

**Problem**: Compiling all patterns upfront wastes time if only few are used.

**Solution**: Compile on first use.

```text
_compiled_cache = {}

def get_pattern(token_type):
    if token_type not in _compiled_cache:
        _compiled_cache[token_type] = re.compile(TOKENS[token_type])
    return _compiled_cache[token_type]
```

**Grammar Characteristics**:
- Line-oriented (most constructs are single lines)
- State-dependent (code fences change interpretation)
- Inline/block distinction (emphasis vs paragraphs)

**Key Grammar Decisions**:
```text
TOKEN_PRECEDENCE = [
    "CODE_FENCE",      # Must be first (changes state)
    "HEADING",         # Specific pattern
    "LIST_ITEM",       # Specific pattern
    "BLANK_LINE",      # Separator
    "TEXT"             # Catch-all
]

GRAMMAR = {
    "document": {"children": ["heading", "paragraph", "list", "code_block"]},
    "paragraph": {"children": ["text"]},  # Inline pass happens in text
}
```

- Indentation-based blocks (Python)

# Python-specific tokens
TOKENS = {

TOKENS = {

## Conclusion

A well-designed **grammar specification** is the cornerstone of robust language processing. By formalizing token patterns, precedence rules, node types, and structural constraints in a single source of truth, you ensure:

- **Consistency** across all pipeline phases
- **Maintainability** through centralized rules
- **Extensibility** via declarative additions
- **Testability** of individual components

**Key Principles**:

1. **Single source of truth**: All phases reference the same grammar
2. **Precedence is order**: Use lists, not dictionaries with priorities
3. **Named capture groups**: Always extract metadata semantically
4. **Specific before general**: Avoid ambiguity through ordering
5. **Separate concerns**: Grammar defines syntax, not semantics

**Implementation Checklist**:

- [ ] Define all token patterns with named groups
- [ ] Establish precedence order (specific → general → catch-all)
- [ ] List all node types for AST
- [ ] Specify structural rules (parent-child relationships)
- [ ] Write tests for pattern matching, precedence, captures
- [ ] Validate grammar against sample inputs
- [ ] Document decisions and trade-offs

**Next Steps**: With grammar defined, proceed to implement the **lexical analyzer** that consumes these specifications and produces tokens.
