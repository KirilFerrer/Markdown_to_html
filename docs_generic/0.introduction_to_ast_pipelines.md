# Introduction to AST-Based Language Processing Pipelines

## [1].motivation_and_purpose

### What is an AST Pipeline?

An **Abstract Syntax Tree (AST) pipeline** is a systematic approach to processing structured languages (programming languages, markup languages, DSLs, configuration formats, etc.) by breaking the transformation into distinct, composable phases.

**Core Concept**: Instead of using regex or ad-hoc string manipulation to directly convert `SOURCE_LANG` → `TARGET_LANG`, we build an intermediate tree representation that captures the syntactic and semantic structure of the source.

```text
SOURCE_LANG  →  Tokens  →  AST  →  Validated AST  →  TARGET_LANG
```

### Why AST Over Direct Transformation?

| Approach | Advantages | Disadvantages |
|----------|-----------|---------------|
| **Direct regex/string manipulation** | Simple for trivial cases | Fragile, hard to extend, no validation |
| **AST-based pipeline** | Extensible, testable, validates structure | More upfront design, steeper learning curve |

**When to use AST pipelines**:
- Complex source language with nested structures
- Need for deep validation (e.g., semantic rules)
- Multiple output targets from same source
- Long-term maintainability required
- Tooling (formatters, linters, optimizers)

**When direct transformation is acceptable**:
- Trivial one-to-one mapping (e.g., CSV → JSON with fixed schema)
- Prototype/throw-away code
- Source has no nested/recursive structures

### Key Benefits of AST Architecture

#### 1. Separation of Concerns

Each phase has a single, well-defined responsibility:

```text
Grammar Definition  → defines what's valid
Lexical Analysis    → identifies tokens
Parsing             → builds structure
Semantic Analysis   → validates rules
Code Generation     → produces output
```

**Benefit**: You can modify parsing without touching validation, or add a new output format without changing the lexer.

#### 2. Extensibility

Adding new features doesn't require rewriting the entire system. Example:

```text
Add "for loop" to custom DSL:
1. Add token patterns to grammar
2. Teach lexer to recognize "for" keyword (automatic if grammar-driven)
3. Add parsing rule for loop structure
4. Add validation rules (e.g., "no infinite loops")
5. Add code generation for loop construct
```

Each change is localized to one module.

#### 3. Deep Validation

AST allows context-aware validation that's impossible with regex:

- **Structural rules**: "Function calls must reference declared functions"
- **Scoping rules**: "Variables must be declared before use"
- **Style rules**: "Indentation must be consistent"

#### 4. Multiple Outputs

Same AST can generate different targets:

```text
Python AST  →  JavaScript (transpiler)
            →  Bytecode (compiler)
            →  Documentation (docgen)
            →  Pretty-printed Python (formatter)
```

## [2].universal_pipeline_architecture

### Canonical Five-Phase Pipeline

```text
┌─────────────────────┐
│  Grammar Definition │  ← Source of truth (token patterns, rules)
└──────────┬──────────┘
           ↓
┌─────────────────────┐
│  Lexical Analysis   │  ← SOURCE_TEXT → list of tokens
│      (Lexer)        │
└──────────┬──────────┘
           ↓
┌─────────────────────┐
│      Parsing        │  ← Tokens → Abstract Syntax Tree
│      (Parser)       │
└──────────┬──────────┘
           ↓
┌─────────────────────┐
│  Semantic Analysis  │  ← Validates AST against rules
│    (Validator)      │
└──────────┬──────────┘
           ↓
┌─────────────────────┐
│  Code Generation    │  ← AST → TARGET_LANG
│    (Renderer)       │
└─────────────────────┘
```

### Data Flow

| Input | Phase | Output |
|-------|-------|--------|
| Raw source text | **Lexical Analysis** | `[{type: TOKEN_TYPE, position: LINE, metadata: {...}}, ...]` |
| List of tokens | **Parsing** | `{type: NODE_TYPE, children: [...], attributes: {...}}` |
| AST | **Semantic Analysis** | AST + `[{error_code, message, location}, ...]` |
| Validated AST | **Code Generation** | Target language string |

### Separation of Responsibilities

| Phase | Responsibility | Does NOT do |
|-------|---------------|-------------|
| **Grammar** | Declares what's valid (data only) | Execute logic |
| **Lexer** | Identifies token types | Group tokens into structures |
| **Parser** | Builds tree structure | Validate semantic rules |
| **Validator** | Checks contextual rules | Modify AST structure |
| **Code Generator** | Produces output | Validate correctness |

**Golden Rule**: Each phase communicates via simple data structures. No shared mutable state, no circular dependencies.

## [3].grammar_definition

### What is a Grammar?

A **grammar** is a formal specification of a language's syntax. It defines:

1. **Lexical rules** (tokens): `IDENTIFIER`, `KEYWORD`, `OPERATOR`, `LITERAL`
2. **Syntactic rules** (structure): "A function is a keyword 'def', identifier, parameters, and body"
3. **Precedence rules**: Which patterns have priority when ambiguous
4. **Node types**: What kinds of AST nodes exist

### Components of a Grammar Specification

#### 3.1. Token Definitions

Patterns that identify atomic elements:

```text
KEYWORD_IF      = /^if\b/
IDENTIFIER      = /^[a-zA-Z_][a-zA-Z0-9_]*/
NUMBER          = /^\d+(\.\d+)?/
OPERATOR_PLUS   = /^\+/
WHITESPACE      = /^\s+/
```

**Key principle**: Use **named capture groups** to extract metadata.

#### 3.2. Precedence Order

List of token types in order of priority (most specific first):

```text
TOKEN_ORDER = [
    "KEYWORD_IF",      # specific: matches only "if"
    "IDENTIFIER",      # general: matches any identifier
    "WHITESPACE",      # catch-all: matches spaces
]
```

**Why order matters**: Without it, "if" would match `IDENTIFIER` before `KEYWORD_IF`.

#### 3.3. Node Types

AST node categories:

```text
NODE_TYPES = [
    "program",           # root
    "function_def",      # function definition
    "if_statement",      # conditional
    "binary_expression", # x + y
    "identifier",        # variable name (leaf)
    "literal",           # constant value (leaf)
]
```

#### 3.4. Structural Rules (Grammar)

Defines valid parent-child relationships:

```text
GRAMMAR = {
    "program": {
        "children": ["function_def", "if_statement"],
        "attributes": []
    },
    "function_def": {
        "children": ["identifier", "parameter_list", "block"],
        "attributes": ["name"]
    },
    "if_statement": {
        "children": ["expression", "block"],
        "attributes": []
    }
}
```

**Usage**: Validator checks that AST conforms to these rules.

### Example: Minimal Math Expression Grammar

```text
TOKENS:
  NUMBER    = /^\d+/
  OPERATOR  = /^[+\-*/]/
  PAREN_L   = /^\(/
  PAREN_R   = /^\)/

TOKEN_ORDER = ["NUMBER", "OPERATOR", "PAREN_L", "PAREN_R"]

NODES:
  expression, binary_op, number

GRAMMAR:
  expression → number | binary_op | "(" expression ")"
  binary_op  → expression OPERATOR expression
  number     → NUMBER
```

**Example input**: `3 + (5 * 2)`

**Expected AST**:
```text
{
  type: "binary_op",
  operator: "+",
  left: {type: "number", value: 3},
  right: {
    type: "binary_op",
    operator: "*",
    left: {type: "number", value: 5},
    right: {type: "number", value: 2}
  }
}
```

## [4].lexical_analysis

### Purpose

Convert raw source text into a sequence of **tokens** (atomic units with semantic meaning).

### What is a Token?

```text
Token = {
    type:     string,   # TOKEN_TYPE from grammar
    value:    string,   # original text
    position: int,      # line/column for errors
    metadata: dict      # extracted data (e.g., number value, identifier name)
}
```

### Example: Lexing a Simple Expression

**Input**: `x = 42 + y`

**Output**:
```text
[
    {type: "IDENTIFIER", value: "x", position: 1, metadata: {name: "x"}},
    {type: "OPERATOR_ASSIGN", value: "=", position: 1, metadata: {}},
    {type: "NUMBER", value: "42", position: 1, metadata: {int_value: 42}},
    {type: "OPERATOR_PLUS", value: "+", position: 1, metadata: {}},
    {type: "IDENTIFIER", value: "y", position: 1, metadata: {name: "y"}}
]
```

### Key Responsibilities

| ✅ Lexer DOES | ❌ Lexer DOES NOT |
|--------------|------------------|
| Identify token types | Parse nested structures |
| Extract metadata from patterns | Validate syntax rules |
| Track source positions | Build AST nodes |
| Handle whitespace policy | Perform semantic checks |

### Token Precedence Example

```text
Input: "if123"

❌ Wrong precedence:
  IDENTIFIER matches "if123" first → wrong

✅ Correct precedence:
  1. Try KEYWORD_IF (matches "if") → fails (followed by "123")
  2. Try IDENTIFIER (matches "if123") → succeeds ✓
```

**Solution**: Keywords must require word boundaries (`\b` in regex).

## [5].parsing

### Purpose

Convert **linear token stream** into **hierarchical AST**.

### Token vs Node

| Concept | Level | Example |
|---------|-------|---------|
| **Token** | Lexical | `{type: "KEYWORD_IF", value: "if", ...}` |
| **Node** | Syntactic | `{type: "if_statement", condition: ..., body: ...}` |

**Key difference**: Tokens represent source text; nodes represent semantic constructs.

### Parsing Strategies

#### Top-Down (Recursive Descent)

Start from root, recursively build children:

```text
function parse_expression():
    left = parse_primary()
    if next_token is OPERATOR:
        op = consume(OPERATOR)
        right = parse_expression()
        return make_node("binary_op", left, op, right)
    return left
```

**Advantages**: Intuitive, mirrors grammar structure.

**Disadvantages**: Can be slow for complex grammars without optimization.

#### Bottom-Up (Shift-Reduce)

Build leaves first, combine into parents:

```text
Stack-based algorithm:
1. Shift tokens onto stack
2. When pattern matches, reduce to node
3. Repeat until single root node
```

**Advantages**: Handles left-recursive grammars, efficient.

**Disadvantages**: Less intuitive, harder to debug.

### Stateful Parsing

Some constructs require tracking context:

- **Strings**: Ignore syntax inside quotes
- **Comments**: Skip until end marker
- **Blocks**: Track nesting depth

```text
state = "normal"
if token.type == "STRING_START":
    state = "inside_string"
    # Accumulate characters until STRING_END
```

### Parser Responsibilities

| ✅ Parser DOES | ❌ Parser DOES NOT |
|---------------|--------------------|
| Group related tokens | Validate semantic rules |
| Build tree structure | Generate output code |
| Handle state (e.g., strings) | Perform type checking |
| Emit well-formed AST | Optimize AST |

## [6].semantic_analysis

### Purpose

Validate that AST conforms to **contextual rules** that depend on surrounding nodes, scope, or previous declarations.

### Lexical vs Syntactic vs Semantic

| Phase | Example Rule |
|-------|-------------|
| **Lexical** | "Keyword 'if' must be followed by whitespace" (pattern) |
| **Syntactic** | "If statement has condition and body" (structure) |
| **Semantic** | "Condition must be boolean expression" (type) |

**Semantic rules cannot be expressed as regex or simple tree structure**.

### Types of Semantic Rules

#### 1. Type Checking

```text
x = "hello" + 42  # ❌ String + Int invalid
```

#### 2. Scope Validation

```text
print(z)  # ❌ Variable 'z' not declared
```

#### 3. Control Flow

```text
return x  # ❌ Return outside function
```

#### 4. Style Rules

```text
function VeryLongFunctionNameThatExceedsLimit() { }  # ⚠️ Name too long
```

### Validator Architecture

**Declarative rule table**:

```text
RULES = {
    "TYPE_001": {
        "name": "binary-op-types",
        "check": lambda node: validate_binary_operands(node)
    },
    "SCOPE_002": {
        "name": "undefined-variable",
        "check": lambda node: validate_variable_declared(node)
    }
}
```

**Traversal**:

```text
function validate(ast):
    errors = []
    context = {scope: [], type_env: {}}
    
    traverse(ast, node):
        for rule in RULES:
            result = rule.check(node, context)
            if not result.ok:
                errors.append(result.error)
    
    return {ast: ast, errors: errors}
```

**Key principle**: Validator **reads** AST, never modifies it. All changes happen in parser or code generator.

## [7].code_generation

### Purpose

Transform AST into target language (code, bytecode, HTML, JSON, etc.).

### Approaches

#### 1. Template-Based

```text
function generate_if(node):
    condition = generate(node.condition)
    body = generate(node.body)
    return f"if ({condition}) {{ {body} }}"
```

**Advantages**: Simple, readable.

**Disadvantages**: Harder to optimize.

#### 2. Visitor Pattern

```text
class CodeGenerator:
    def visit_if_statement(node):
        # Generate if
    
    def visit_function_def(node):
        # Generate function
```

**Advantages**: Extensible, organized.

**Disadvantages**: More boilerplate.

#### 3. IR-Based (Intermediate Representation)

```text
AST → IR (simplified) → TARGET_LANG
```

**Advantages**: Enables optimization passes.

**Disadvantages**: Added complexity.

### Example: Python → JavaScript

**Python AST**:
```text
{
  type: "function_def",
  name: "add",
  params: ["a", "b"],
  body: {type: "return", value: {type: "binary_op", op: "+", left: "a", right: "b"}}
}
```

**Generated JavaScript**:
```javascript
function add(a, b) {
    return a + b;
}
```

### Safety Considerations

- **Escape special characters**: HTML entities, SQL injection, etc.
- **Validate identifiers**: Don't emit `function 123invalid() {}`
- **Handle edge cases**: Empty blocks, null values

## [8].implementation_strategies

### Functional vs OOP

| Aspect | Functional | Object-Oriented |
|--------|-----------|-----------------|
| **State** | Immutable data structures | Mutable objects |
| **Composition** | Higher-order functions | Inheritance/interfaces |
| **Testing** | Pure functions (input→output) | Mock objects |
| **AST representation** | Nested dicts/lists | Node class hierarchy |

**Recommendation**: For smaller projects, functional is simpler. For large compilers (e.g., TypeScript), OOP provides better organization.

### Error Recovery

**Strategies when encountering invalid syntax**:

1. **Panic mode**: Skip tokens until synchronization point (e.g., semicolon)
2. **Error productions**: Grammar includes common mistakes
3. **Tolerant parsing**: Emit partial AST with error markers

**Example**:
```text
Input: "x = ;"  # Missing value

Panic mode: Skip to next statement
Tolerant: Emit {type: "assignment", left: "x", right: {type: "ERROR"}}
```

### Performance Optimization

| Technique | Use Case |
|-----------|----------|
| **Memoization** | Recursive parsing with redundant subproblems |
| **Parallel lexing** | Large files split into chunks |
| **Lazy parsing** | Parse function bodies only when accessed |
| **Compiled regex** | Precompile patterns once at startup |

## [9].practical_use_cases

### Case 1: Markdown → HTML

- **Grammar**: Headings, lists, code blocks, emphasis
- **Lexer**: Line-by-line token identification
- **Parser**: Group consecutive lines into paragraphs
- **Validator**: Check heading levels, list indentation
- **Generator**: Emit HTML with proper escaping

**Complexity**: Medium (state for code blocks, inline parsing)

### Case 2: Python → JavaScript Transpiler

- **Grammar**: Python syntax (subset: functions, if/for, expressions)
- **Lexer**: Indentation-aware tokenization
- **Parser**: Build AST from indented blocks
- **Validator**: Type checking (optional), scope validation
- **Generator**: Emit ES6 JavaScript

**Complexity**: High (Python's significant whitespace, comprehensions)

### Case 3: SQL → AST (Query Optimizer)

- **Grammar**: SELECT, FROM, WHERE, JOIN, etc.
- **Lexer**: Keywords, identifiers, operators, strings
- **Parser**: Build query tree (SELECT → table, columns, conditions)
- **Validator**: Column existence, type compatibility
- **Generator**: Optimized SQL or execution plan

**Complexity**: High (complex precedence, correlated subqueries)

### Case 4: CSS → Minimized CSS

- **Grammar**: Selectors, properties, values
- **Lexer**: Tokenize selectors, braces, properties
- **Parser**: Build stylesheet tree
- **Validator**: Valid property names, vendor prefixes
- **Generator**: Minified CSS (no whitespace, short names)

**Complexity**: Low (flat structure, no nested logic)

### Case 5: Custom DSL → Python Code

Example DSL: Configuration for data pipelines

```text
source "users_db" {
    query = "SELECT * FROM users"
}

transform "filter_active" {
    condition = "status == 'active'"
}

output "csv" {
    path = "active_users.csv"
}
```

- **Grammar**: Blocks with identifiers and key-value pairs
- **Lexer**: Keywords (source, transform, output), identifiers, strings
- **Parser**: Build pipeline AST (list of stages)
- **Validator**: Valid stages, required fields, file paths exist
- **Generator**: Python script with function calls

**Complexity**: Low-Medium (simple structure, minimal nesting)

### Case 6: JSON Schema → Validation Code

- **Grammar**: JSON schema format (type, properties, required, etc.)
- **Lexer**: Standard JSON lexing
- **Parser**: Build schema AST
- **Validator**: Schema correctness (valid types, no cycles)
- **Generator**: Python/JavaScript validation functions

**Complexity**: Medium (recursive schemas, references)

## [10].testing_and_validation

### Test Each Phase Independently

```text
# Lexer test
assert tokenize("x = 42") == [
    {type: "IDENTIFIER", ...},
    {type: "OPERATOR_ASSIGN", ...},
    {type: "NUMBER", ...}
]

# Parser test
ast = parse(tokenize("x = 42"))
assert ast.type == "assignment"
assert ast.left.name == "x"

# Validator test
errors = validate(malformed_ast)
assert "undefined-variable" in [e.code for e in errors]

# Generator test
code = generate(ast)
assert code == "x = 42;"
```

### Canonical Test Cases

| Test Type | Purpose |
|-----------|---------|
| **Minimal valid** | Smallest valid input (e.g., single token) |
| **Edge cases** | Empty input, maximum nesting, long identifiers |
| **Error cases** | Invalid syntax, semantic errors |
| **Regression** | Previously found bugs |
| **Golden files** | Large real-world samples with expected output |

### Property-Based Testing

Generate random valid inputs, assert invariants:

```text
property: lex(render(ast)) == lex(original_source)  # Roundtrip
property: validate(parse(tokenize(input))) has no errors  # Valid input → valid AST
```

## [11].common_pitfalls

### Pitfall 1: Mixing Concerns

❌ **Bad**: Lexer performs validation
```text
if token.type == "NUMBER" and int(token.value) > MAX_INT:
    raise ValueError("Number too large")
```

✅ **Good**: Lexer emits token, validator checks range

### Pitfall 2: Ambiguous Grammar

❌ **Bad**: Order-dependent token precedence undocumented
```text
TOKENS = {
    "IDENTIFIER": /^\w+/,
    "KEYWORD": /^if|else/  # Never matches because IDENTIFIER comes first
}
```

✅ **Good**: Explicit precedence, specific before general

### Pitfall 3: No Error Recovery

❌ **Bad**: Parser crashes on first syntax error
```text
if not match("SEMICOLON"):
    raise SyntaxError()  # Entire parse fails
```

✅ **Good**: Emit error, continue parsing
```text
if not match("SEMICOLON"):
    errors.append({code: "missing-semicolon", ...})
    # Continue to find more errors
```

### Pitfall 4: Mutation in Validator

❌ **Bad**: Validator modifies AST
```text
if node.type == "identifier" and node.name == "old":
    node.name = "new"  # Wrong phase!
```

✅ **Good**: Validator only reports issues, parser handles corrections

### Pitfall 5: Tight Coupling

❌ **Bad**: Lexer imports parser, parser imports validator
```text
from parser import check_valid_token  # Circular dependency
```

✅ **Good**: Linear dependency: Grammar ← Lexer ← Parser ← Validator ← Generator

## Conclusion

AST-based pipelines provide a **robust, extensible architecture** for language processing. By separating concerns into distinct phases—grammar definition, lexical analysis, parsing, semantic analysis, and code generation—you gain:

- **Maintainability**: Each phase is independently testable and modifiable
- **Extensibility**: Adding features doesn't require rewriting the entire system
- **Validation**: Deep semantic rules enforced declaratively
- **Multiple outputs**: Same AST generates different target formats

**Core Principles to Remember**:

1. **Single source of truth** (grammar) defines what's valid
2. **Each phase has one responsibility** and doesn't invade others
3. **Data flows linearly** through phases (no circular dependencies)
4. **Validate late** (lexer/parser build structure, validator checks rules)
5. **Test each phase** independently with clear input/output contracts

**When to Use This Architecture**:
- Source language has nested/recursive structures
- Need for comprehensive error reporting
- Multiple output formats required
- Long-term project with evolving requirements

**When to Skip**:
- Trivial one-to-one transformations
- Prototype code with no maintenance plans
- Performance-critical real-time processing (consider simpler approaches first)

**Next Steps**: Choose a source language, define its grammar formally, then implement each phase incrementally. Start with a minimal MVP (e.g., 3 token types, 2 node types) and expand iteratively.

Happy parsing! 🚀
