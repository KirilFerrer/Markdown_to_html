# Lexical Analysis: From Source Text to Tokens

## [1].role_in_pipeline

### Position in the Processing Chain

The **lexical analyzer** (lexer, tokenizer, or scanner) is the first active phase of language processing. While the grammar defines what's valid, the lexer **applies those definitions** to transform raw source text into a structured token stream.

```text
┌──────────────────────┐
│  Grammar Definition  │  ← Source of truth (data only)
└──────────┬───────────┘
           ↓ referenced by
┌──────────────────────┐
│  Lexical Analyzer    │  ← Identifies and classifies characters/lines
└──────────┬───────────┘
           ↓ token stream
┌──────────────────────┐
│      Parser          │  ← Builds AST from tokens
└──────────────────────┘
```

**Analogy**: The lexer is like a reader identifying words in a sentence. The parser then understands how those words combine into meaningful phrases.

### Why a Separate Lexical Phase?

**Without lexer** (parser handles everything):
```text
Parser reads: "if (x > 5) { return x; }"
  - Must recognize keywords, operators, delimiters, identifiers
  - Must handle whitespace, comments
  - Must track character positions for errors
  - Violates separation of concerns
```

**With lexer**:
```text
Lexer produces: [KEYWORD_IF, LPAREN, IDENTIFIER, OPERATOR_GT, NUMBER, RPAREN, ...]
Parser consumes: Tokens (abstracted from character-level details)
  - Parser focuses on syntax structure
  - Lexer handles character-level concerns
  - Clean separation
```

### Benefits of Grammar-Driven Lexer

A **generic lexer** consults the grammar for patterns and precedence, rather than hardcoding language-specific logic.

| Aspect | Hardcoded Lexer | Grammar-Driven Lexer |
|--------|-----------------|----------------------|
| **Adding tokens** | Modify lexer code | Add to grammar only |
| **Changing precedence** | Reorder if/else chains | Reorder grammar list |
| **Testing** | Test lexer implementation | Test grammar patterns |
| **Reusability** | Tied to one language | Works for any grammar |

**Example**:
```text
// Hardcoded (❌)
if (char == '+') return PLUS;
else if (char == '*') return MULT;

// Grammar-driven (✅)
for (token_type, pattern) in GRAMMAR.tokens:
    if pattern.match(input):
        return token_type
```

## [2].responsibilities_and_boundaries

### Input and Output

| Aspect | Details |
|--------|---------|
| **Input** | Raw source text (string, file, stream) |
| **Output** | Sequence of tokens: `[{type, value, position, metadata}, ...]` |
| **Processing** | Every character/line is accounted for |
| **Guarantee** | No information loss (can reconstruct original from tokens) |

**Example Flow**:
```text
Input: "x = 42 + y"

Output:
[
    {type: "IDENTIFIER", value: "x", position: {line: 1, col: 1}, metadata: {name: "x"}},
    {type: "ASSIGN", value: "=", position: {line: 1, col: 3}, metadata: {}},
    {type: "NUMBER", value: "42", position: {line: 1, col: 5}, metadata: {int_value: 42}},
    {type: "PLUS", value: "+", position: {line: 1, col: 8}, metadata: {}},
    {type: "IDENTIFIER", value: "y", position: {line: 1, col: 10}, metadata: {name: "y"}}
]
```

### What Lexer DOES

| Responsibility | Example |
|----------------|---------|
| **Identify token types** | "if" → KEYWORD, "x" → IDENTIFIER |
| **Extract metadata** | "42" → {int_value: 42} |
| **Track positions** | Column/line numbers for error messages |
| **Handle whitespace** | Skip or preserve based on grammar rules |
| **Simple state management** | String literals, multi-line comments |

### What Lexer DOES NOT Do

| Not Its Job | Whose Job? |
|-------------|-----------|
| Build AST nodes | Parser |
| Group related tokens | Parser |
| Validate semantic rules | Validator |
| Check type compatibility | Type checker |
| Generate output code | Code generator |

**Critical Principle**: **Lexer is tolerant**. If no pattern matches, emit a fallback token (e.g., `UNKNOWN` or `TEXT`). Never crash. Let the validator report errors.

### Boundary with Parser

**Lexer ends**: When all input is converted to tokens with types and metadata.

**Parser starts**: When tokens are grouped into hierarchical structures.

**Example Boundary**:
```text
Source: "function add(x, y) { return x + y; }"

Lexer output: [KEYWORD_FUNCTION, IDENTIFIER, LPAREN, IDENTIFIER, COMMA, IDENTIFIER, RPAREN, ...]

Parser input: Token stream
Parser output: AST node {type: "function_def", name: "add", params: [...], body: ...}
```

## [3].tokenization_strategies

### Strategy 1: Character-by-Character Scanning

**Approach**: Advance one character at a time, building tokens incrementally.

**Pseudocode**:
```text
function tokenize(source):
    tokens = []
    position = 0
    
    while position < len(source):
        char = source[position]
        
        if is_whitespace(char):
            position += 1  # Skip
        elif is_digit(char):
            token = scan_number(source, position)
            tokens.append(token)
            position = token.end_position
        elif is_letter(char):
            token = scan_identifier(source, position)
            tokens.append(token)
            position = token.end_position
        elif char == '+':
            tokens.append({type: "PLUS", value: "+", position: position})
            position += 1
        # ... other cases
    
    return tokens
```

**Advantages**:
- Full control over character-level logic
- Handles complex lexical rules (e.g., Python indentation)

**Disadvantages**:
- Verbose for simple grammars
- Easy to introduce bugs

**Best for**: Languages with complex lexical rules (Python, Haskell).

### Strategy 2: Regex-Based Matching

**Approach**: Use regular expressions to match token patterns.

**Pseudocode**:
```text
function tokenize(source):
    tokens = []
    position = 0
    
    TOKEN_PATTERNS = [
        ("NUMBER", r"\d+(\.\d+)?"),
        ("IDENTIFIER", r"[a-zA-Z_]\w*"),
        ("PLUS", r"\+"),
        ("WHITESPACE", r"\s+")
    ]
    
    while position < len(source):
        matched = False
        
        for (token_type, pattern) in TOKEN_PATTERNS:
            match = regex_match_at(pattern, source, position)
            if match:
                if token_type != "WHITESPACE":  # Skip whitespace
                    tokens.append({
                        type: token_type,
                        value: match.text,
                        position: position
                    })
                position = match.end
                matched = True
                break
        
        if not matched:
            # Fallback for unrecognized character
            tokens.append({type: "UNKNOWN", value: source[position], position: position})
            position += 1
    
    return tokens
```

**Advantages**:
- Concise, declarative
- Easy to modify patterns

**Disadvantages**:
- Regex overhead for each match
- Harder to handle context-dependent rules

**Best for**: Languages with regular lexical structure (JSON, XML, simple DSLs).

### Strategy 3: Hybrid (DFA + Special Cases)

**Approach**: Use Deterministic Finite Automaton (DFA) for most tokens, handle edge cases manually.

**Pseudocode**:
```text
function tokenize(source):
    tokens = []
    position = 0
    state = "START"
    
    while position < len(source):
        char = source[position]
        
        if state == "START":
            if is_digit(char):
                state = "NUMBER"
                buffer = char
            elif is_letter(char):
                state = "IDENTIFIER"
                buffer = char
            elif char == '/':
                state = "SLASH"  # Could be division or comment
                buffer = char
            # ...
        
        elif state == "NUMBER":
            if is_digit(char) or char == '.':
                buffer += char
            else:
                tokens.append({type: "NUMBER", value: buffer})
                state = "START"
                continue  # Don't advance position
        
        # ... other states
        
        position += 1
    
    return tokens
```

**Advantages**:
- Efficient (O(n) single pass)
- Fine-grained control

**Disadvantages**:
- Complex state machine code
- Hard to maintain

**Best for**: Production compilers (C, Java).

### Comparison Table

| Strategy | Simplicity | Performance | Flexibility | Best Use Case |
|----------|-----------|-------------|-------------|---------------|
| **Character-by-character** | Medium | Slow | High | Complex languages |
| **Regex-based** | High | Medium | Medium | Simple DSLs |
| **DFA-based** | Low | Fast | Low | Production compilers |

## [4].token_structure

### Canonical Token Format

Every token should have:

```text
Token = {
    type:     string,       # TOKEN_TYPE from grammar
    value:    string,       # Original text from source
    position: {             # Location in source (for errors)
        line:   int,
        column: int
    },
    metadata: dict          # Extracted data (type-specific)
}
```

### Field Descriptions

| Field | Purpose | Example |
|-------|---------|---------|
| `type` | Classification for parser | "KEYWORD_IF", "IDENTIFIER", "NUMBER" |
| `value` | Original source text | "42", "function", "x" |
| `position` | Error reporting | {line: 5, column: 12} |
| `metadata` | Parsed/normalized data | {int_value: 42}, {name: "x"} |

### Why Preserve Original Value?

**Reason 1: Debugging**

If normalization introduces bugs, you can compare normalized vs original.

```text
Token: {
    type: "NUMBER",
    value: "3.14159",  # Original
    metadata: {float_value: 3.14}  # Rounded
}

Debug: "Why did calculation fail?"
Check: Original value shows full precision was in source.
```

**Reason 2: Error Messages**

Point user to exact text they wrote.

```text
Error at line 10, column 5: Invalid identifier "123abc"
          (points to original token.value)
```

**Reason 3: Roundtrip Preservation**

Enable `render(parse(lex(source))) == source` (formatting tools).

### Metadata Extraction

Use **named capture groups** in regex:

```text
PATTERN = r"^(?P<value>\d+)$"

match = PATTERN.match("42")
metadata = match.groupdict()  # {"value": "42"}
```

**Type-specific metadata**:

```text
NUMBER token:
  metadata = {int_value: 42, float_value: 42.0}

IDENTIFIER token:
  metadata = {name: "x", is_keyword: False}

STRING token:
  metadata = {unescaped_value: "hello\nworld", quote_style: "double"}
```

### Mini-Example: 3 Tokens

**Input**: `x = 42`

**Tokens**:
```text
[
    {
        type: "IDENTIFIER",
        value: "x",
        position: {line: 1, column: 1},
        metadata: {name: "x"}
    },
    {
        type: "ASSIGN",
        value: "=",
        position: {line: 1, column: 3},
        metadata: {}
    },
    {
        type: "NUMBER",
        value: "42",
        position: {line: 1, column: 5},
        metadata: {int_value: 42}
    }
]
```

## [5].state_management

### When State is Necessary

Most tokens are **context-independent** (a keyword is always a keyword). But some constructs require **state**:

| Construct | Why State Needed |
|-----------|------------------|
| **String literals** | Ignore syntax inside quotes: `"function x() {"` |
| **Multi-line comments** | Span multiple lines: `/* ... \n ... */` |
| **Heredocs** | Multi-line strings with delimiters |
| **Indentation blocks** | Python, YAML: track indent level |
| **Escape sequences** | Inside strings: `"\n"` vs outside: `\n` |

### State Machine Approach

**Example: String Literals**

```text
States: NORMAL, INSIDE_STRING

function tokenize(source):
    state = NORMAL
    tokens = []
    buffer = ""
    
    for char in source:
        if state == NORMAL:
            if char == '"':
                state = INSIDE_STRING
                buffer = '"'
            elif is_letter(char):
                # Scan identifier
                ...
        
        elif state == INSIDE_STRING:
            buffer += char
            if char == '"':
                # Check if escaped
                if not is_escaped(buffer):
                    tokens.append({type: "STRING", value: buffer})
                    buffer = ""
                    state = NORMAL
```

### Example: Python Indentation

Python uses indentation for blocks, requiring indent stack tracking.

```text
State: indent_stack = [0]  # Current indentation levels

function tokenize_line(line):
    indent = count_leading_spaces(line)
    current_indent = indent_stack[-1]
    
    if indent > current_indent:
        # Indent increased
        emit_token(INDENT)
        indent_stack.append(indent)
    
    elif indent < current_indent:
        # Dedent (possibly multiple levels)
        while indent_stack[-1] > indent:
            emit_token(DEDENT)
            indent_stack.pop()
    
    # Now tokenize the rest of the line normally
```

### Example: Multi-line Comments

```text
State: inside_comment = False

function tokenize(source):
    position = 0
    inside_comment = False
    
    while position < len(source):
        if not inside_comment:
            if source[position:position+2] == "/*":
                inside_comment = True
                position += 2
            else:
                # Normal tokenization
                ...
        else:
            if source[position:position+2] == "*/":
                inside_comment = False
                position += 2
            else:
                # Skip characters inside comment
                position += 1
```

### Minimal State Principle

**Only track state when absolutely necessary**. Excessive state complicates the lexer.

| ✅ Good State Use | ❌ Unnecessary State |
|-------------------|---------------------|
| String literal delimiters | Counting operators (parser's job) |
| Multi-line comment tracking | Tracking function nesting (parser's job) |
| Python indent levels | Validating syntax (validator's job) |

## [6].whitespace_handling

### Strategies

#### Strategy 1: Ignore Completely

**Use case**: C, Java, JavaScript (whitespace not syntactically significant).

```text
function tokenize(source):
    for char in source:
        if is_whitespace(char):
            continue  # Skip
        else:
            # Tokenize non-whitespace
```

#### Strategy 2: Emit WHITESPACE Tokens

**Use case**: Formatters, linters (preserve spacing).

```text
TOKENS = [
    ... other tokens ...,
    ("WHITESPACE", r"\s+")
]

# Parser filters out WHITESPACE if not needed
```

#### Strategy 3: Syntactically Significant

**Use case**: Python, YAML (indentation matters).

```text
# Emit INDENT/DEDENT tokens based on indentation changes
# (see state management section above)
```

#### Strategy 4: Normalize

**Use case**: Markdown (collapse multiple spaces).

```text
function tokenize_line(line):
    normalized = line.strip()  # Remove leading/trailing
    # Tokenize normalized version
```

### Newline Handling

| Language | Newline Treatment |
|----------|-------------------|
| **C, Java** | Whitespace (ignored) |
| **JavaScript** | Sometimes significant (automatic semicolon insertion) |

## [7].error_recovery

### Philosophy: Tolerant Lexer

**Principle**: Lexer should **never crash**. If input doesn't match any pattern, emit fallback token and continue.

**Why?**
- Single lexical error shouldn't halt entire compilation
- Better error reporting: find multiple issues at once
- Enables "error-tolerant" parsing for IDEs

### Fallback Strategies

#### Strategy 1: UNKNOWN Token

```text
function identify_token(text, position):
    for (token_type, pattern) in TOKEN_PATTERNS:
        match = pattern.match(text, position)
        if match:
            return {type: token_type, ...}
    
    # No match: emit UNKNOWN
    return {
        type: "UNKNOWN",
        value: text[position],
        position: position,
        metadata: {error: "Unrecognized character"}
    }
```

**Validator later reports**: `"Invalid token UNKNOWN at line 5: '@'"`

#### Strategy 2: Panic Mode

Skip characters until reaching a synchronization point (e.g., semicolon, newline).

```text
function tokenize_with_panic(source):
    try:
        # Normal tokenization
    except LexError:
        # Skip until next synchronization point
        position = find_next(source, position, sync_chars=[';', '\n'])
        emit_token(ERROR, ...)
        continue
```

#### Strategy 3: Error Productions

Grammar includes common mistakes:

```text
TOKENS = [
    ("NUMBER", r"\d+"),
    ("INVALID_NUMBER", r"\d+[a-zA-Z]+")  # Common mistake: "42abc"
]

# Lexer matches INVALID_NUMBER
# Validator reports: "Invalid number format: cannot contain letters"
```

### Error Messages

**Good error**:
```text
Lexical error at line 10, column 5:
  Unexpected character '@' in identifier
  
  function @invalidName() {
           ^
```

**Bad error**:
```text
LexError: char '@' not recognized
```

## [8].performance_optimization

### Technique 1: Pre-compile Regex

**Problem**: Compiling regex on every match is slow.

**Solution**: Compile once at module load.

```text
# At module level (runs once)
COMPILED_PATTERNS = [
    (token_type, re.compile(pattern))
    for (token_type, pattern) in TOKEN_PATTERNS
]

# In tokenize loop (fast)
for (token_type, compiled_pattern) in COMPILED_PATTERNS:
    match = compiled_pattern.match(source, position)
```

**Speedup**: 10-100x for complex patterns.

### Technique 2: Master Regex

**Problem**: Testing N patterns sequentially is O(N).

**Solution**: Combine all patterns into one with alternation.

```text
MASTER_PATTERN = re.compile(
    r"(?P<NUMBER>\d+)|(?P<IDENTIFIER>[a-zA-Z_]\w*)|(?P<PLUS>\+)"
)

match = MASTER_PATTERN.match(source, position)
if match:
    token_type = match.lastgroup  # Identifies which pattern matched
```

**Speedup**: O(1) regex engine optimization.

### Technique 3: Trie for Keywords

**Problem**: Long keyword lists require many comparisons.

**Solution**: Build prefix tree (trie).

```text
KEYWORDS = {"if", "else", "function", "return", "while"}

keyword_trie = build_trie(KEYWORDS)

# Match in O(k) where k = keyword length
if lookup_trie(keyword_trie, identifier):
    return KEYWORD
else:
    return IDENTIFIER
```

### Technique 4: Lookahead Buffering

**Problem**: Reading character-by-character from file is slow.

**Solution**: Buffer chunks (e.g., 4KB).

```text
buffer = source.read(4096)
position = 0

while position < len(buffer):
    # Process buffer
    if position + 100 > len(buffer):
        buffer = buffer[position:] + source.read(4096)
        position = 0
```

### Technique 5: Parallel Lexing

**Problem**: Large files take long to lex sequentially.

**Solution**: Split into chunks, lex in parallel (for line-oriented languages).

```text
chunks = split_source_by_line(source, num_chunks=CPU_COUNT)

token_lists = parallel_map(tokenize_chunk, chunks)

tokens = flatten(token_lists)
```

**Limitation**: Doesn't work for languages with cross-line state (e.g., multi-line comments).

## [9].language_specific_examples

### Example 1: JSON Lexer

**Grammar**:
```text
TOKENS = {
    "LBRACE": r"\{",
    "RBRACE": r"\}",
    "LBRACKET": r"\[",
    "RBRACKET": r"\]",
    "COLON": r":",
    "COMMA": r",",
    "STRING": r'"([^"\\]|\\.)*"',
    "NUMBER": r"-?\d+(\.\d+)?([eE][+-]?\d+)?",
    "TRUE": r"true",
    "FALSE": r"false",
    "NULL": r"null",
    "WHITESPACE": r"\s+"
}
```

**Lexer pseudocode**:
```text
function tokenize_json(source):
    position = 0
    tokens = []
    
    while position < len(source):
        # Try each pattern
        matched = False
        for (token_type, pattern) in TOKENS:
            match = pattern.match(source, position)
            if match:
                if token_type != "WHITESPACE":
                    tokens.append({type: token_type, value: match.text})
                position = match.end
                matched = True
                break
        
        if not matched:
            raise LexError(f"Invalid character at {position}")
    
    return tokens
```

**Simplicity**: JSON lexical structure is regular, no state needed.

### Example 2: Python Lexer (Indentation)

**Key Challenge**: Track indentation for INDENT/DEDENT tokens.

**State**:
```text
indent_stack = [0]  # Stack of indentation levels
```

**Pseudocode**:
```text
function tokenize_python(source):
    lines = source.splitlines()
    tokens = []
    indent_stack = [0]
    
    for line in lines:
        # Measure indentation
        stripped = line.lstrip()
        indent = len(line) - len(stripped)
        
        # Handle indent changes
        if indent > indent_stack[-1]:
            tokens.append({type: "INDENT"})
            indent_stack.append(indent)
        elif indent < indent_stack[-1]:
            while indent_stack[-1] > indent:
                tokens.append({type: "DEDENT"})
                indent_stack.pop()
        
        # Tokenize the rest of the line normally
        tokens += tokenize_line(stripped)
        tokens.append({type: "NEWLINE"})
    
    # Emit remaining DEDENTs
    while len(indent_stack) > 1:
        tokens.append({type: "DEDENT"})
        indent_stack.pop()
    
    return tokens
```

### Example 3: C Preprocessor

**Challenge**: Handle directives (`#include`, `#define`).

**Strategy**: Lex directives separately before main lexing.

```text
function tokenize_c(source):
    # Phase 1: Preprocess directives
    lines = source.splitlines()
    processed_lines = []
    
    for line in lines:
        if line.startswith("#"):
            handle_directive(line)
        else:
            processed_lines.append(line)
    
    # Phase 2: Normal lexing
    source_without_directives = "\n".join(processed_lines)
    return tokenize_normal(source_without_directives)
```

### Example 4: SQL (Case-Insensitive)

**Challenge**: `SELECT`, `Select`, `select` are equivalent.

**Solution**: Normalize or use case-insensitive regex.

```text
TOKENS = {
    "SELECT": r"(?i:select)\b",  # (?i:...) = case-insensitive
    "FROM": r"(?i:from)\b",
    "WHERE": r"(?i:where)\b",
    "IDENTIFIER": r"[a-zA-Z_]\w*"  # Case-sensitive
}

TOKEN_PRECEDENCE = ["SELECT", "FROM", "WHERE", "IDENTIFIER"]
```

### Example 5: Markdown (Line-Oriented)

**Challenge**: Context-dependent syntax (e.g., `*` as list marker vs emphasis).

**Strategy**: Lex line-by-line with state for code fences.

```text
function tokenize_markdown(source):
    lines = source.splitlines()
    tokens = []
    inside_code_fence = False
    
    for (line_num, line) in enumerate(lines):
        if line.startswith("```"):
            if inside_code_fence:
                tokens.append({type: "CODE_FENCE_END", line: line_num})
                inside_code_fence = False
            else:
                tokens.append({type: "CODE_FENCE_START", line: line_num})
                inside_code_fence = True
        
        elif inside_code_fence:
            tokens.append({type: "CODE_LINE", value: line, line: line_num})
        
        elif line.startswith("#"):
            tokens.append({type: "HEADING", value: line, line: line_num})
        
        elif line.strip() == "":
            tokens.append({type: "BLANK_LINE", line: line_num})
        
        else:
            tokens.append({type: "TEXT", value: line, line: line_num})
    
    return tokens
```

### Example 6: DSL for Configuration

**Example DSL**:
```text
server "web" {
    port = 8080
    host = "localhost"
}
```

**Tokens**:
```text

    "KEYWORD_SERVER": r"server\b",

    "STRING": r'"[^"]*"',
    "NUMBER": r"\d+",
    "EQUALS": r"=",
    "LBRACE": r"\{",
    "RBRACE": r"\}"
}
```

**Lexer output**:

    {type: "KEYWORD_SERVER"},
    {type: "STRING", value: '"web"'},
    {type: "LBRACE"},
    {type: "IDENTIFIER", value: "port"},
    {type: "EQUALS"},
    {type: "NUMBER", value: "8080"},
    ...
]
```

## [10].testing_strategies

### Unit Tests for Individual Patterns

Test each token pattern in isolation.

```text
def test_number_pattern():
    pattern = compile(GRAMMAR.TOKENS["NUMBER"])
    
    # Valid cases
    assert pattern.match("42")
    assert pattern.match("3.14")
    assert pattern.match("-10")
    assert pattern.match("1e10")
    
    # Invalid cases
    assert not pattern.match("abc")
    assert not pattern.match("42abc")
```

### Integration Tests for Token Streams

Test complete lexing with known inputs.

```text
def test_expression_lexing():
    source = "x = 42 + y"
    tokens = tokenize(source)
    
    assert tokens[0].type == "IDENTIFIER"
    assert tokens[0].metadata["name"] == "x"
    
    assert tokens[1].type == "ASSIGN"
    
    assert tokens[2].type == "NUMBER"
    assert tokens[2].metadata["int_value"] == 42
    
    assert tokens[3].type == "PLUS"
    
    assert tokens[4].type == "IDENTIFIER"
    assert tokens[4].metadata["name"] == "y"
```

### Error Handling Tests

Verify lexer handles invalid input gracefully.

```text
def test_invalid_character():
    source = "x = @invalid"
    tokens = tokenize(source)
    
    # Should emit UNKNOWN token, not crash
    unknown_token = [t for t in tokens if t.type == "UNKNOWN"][0]
    assert unknown_token.value == "@"
```

### Precedence Tests

Verify specific patterns win over general patterns.

```text
def test_keyword_before_identifier():
    source = "function"
    tokens = tokenize(source)
    
    # "function" should be KEYWORD, not IDENTIFIER
    assert tokens[0].type == "KEYWORD_FUNCTION"
```

## [11].common_pitfalls

### Pitfall 1: Precedence Errors

❌ **Bad**: Catch-all before specific patterns

```text
TOKEN_PRECEDENCE = [
    "TEXT",        # ❌ Matches everything
    "KEYWORD",     # Never reached
]
```

✅ **Good**: Specific before general

```text
TOKEN_PRECEDENCE = [
    "KEYWORD",
    "IDENTIFIER",
    "TEXT"
]
```

### Pitfall 2: Regex Without Anchors

❌ **Bad**: Pattern matches anywhere

```text
"NUMBER": r"\d+"  # Matches "3" in "abc3def"
```

✅ **Good**: Anchored or with boundaries

```text
"NUMBER": r"^\d+"  # Matches only at current position
```

### Pitfall 3: State Leakage

❌ **Bad**: State persists across lexing calls

```text
inside_string = False  # Global variable

def tokenize(source):
    global inside_string  # ❌ Leaks across calls
```

✅ **Good**: State local to invocation

```text
def tokenize(source):
    state = {"inside_string": False}  # Local state
```

### Pitfall 4: Losing Position Information

❌ **Bad**: No position tracking

```text
return {type: "NUMBER", value: "42"}
# Can't report errors accurately
```

✅ **Good**: Track line/column

```text
return {
    type: "NUMBER",
    value: "42",
    position: {line: 5, column: 10}
}
```

### Pitfall 5: Mixing Lexing and Parsing

❌ **Bad**: Lexer builds AST nodes

```text
if token.type == "KEYWORD_FUNCTION":
    # ❌ Don't do this in lexer
    node = {type: "function_def", ...}
```

✅ **Good**: Lexer only emits tokens

```text
if match("KEYWORD_FUNCTION"):
    return {type: "KEYWORD_FUNCTION", ...}
# Parser builds AST nodes
```

## Conclusion

Lexical analysis is the **foundation** of language processing. A well-designed lexer:

- **Separates concerns**: Character-level details isolated from syntax analysis
- **Enables tolerance**: Gracefully handles invalid input, enabling better error reporting
- **Maintains simplicity**: Grammar-driven design keeps lexer generic and reusable
- **Preserves information**: Tracks positions, original text, and metadata for downstream phases

**Core Principles**:

1. **Grammar-driven**: Consult grammar for patterns and precedence, don't hardcode
2. **Tolerant**: Never crash; emit fallback tokens for unrecognized input
3. **Minimal state**: Only track state when absolutely necessary (strings, comments, indentation)
4. **Position tracking**: Always record line/column for error reporting
5. **Metadata extraction**: Use named capture groups for type-specific data

**Implementation Checklist**:

- [ ] Choose tokenization strategy (regex, character-by-character, DFA)
- [ ] Define token structure (type, value, position, metadata)
- [ ] Implement grammar-driven pattern matching
- [ ] Handle whitespace according to language rules
- [ ] Implement state management for multi-line constructs
- [ ] Add error recovery (fallback tokens)
- [ ] Write unit tests for patterns and precedence
- [ ] Optimize (compile regex, master pattern, trie)

**Next Steps**: With tokens produced, proceed to **parsing** to build the Abstract Syntax Tree.
